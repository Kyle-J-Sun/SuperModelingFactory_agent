# Known gotchas — a history log, not a current-state list

Every entry is tagged with when it was true. **Before repeating one of these to the user, check whether the installed version is at or past the fix** (introspect the relevant source — `inspect.getsource`) and say so either way: "this was real before v0.3.X, confirmed fixed in your current source" is a better answer than silently re-warning about something already closed, and better than silently assuming it's fixed without checking.

## Reject inference direction bugs (fixed 0.3.3)

Root cause across all of these: `Sample.Reject_Infer`'s inferrers were written assuming "higher score = lower risk," while `RejectInferencePipeline` fed them `prescore_prob` = P(bad) — the opposite polarity — with no parameter to reconcile the two.

- **HardCutoffInferrer** — `target = (score < cutoff)` under P(bad) input flags the *safest* rejects as bad and vice versa. Symptom that gave it away: inferred reject bad-rate came out *lower* than the real approved bad-rate, which makes no business sense (rejects should look worse, not better).
- **FuzzyAugmentInferrer** — rejected pseudo-label was `1 - score` (wrong direction, and continuous rather than a proper good/bad split); approved-row reweighting formula additionally suppressed toward zero any real row the prescore had misjudged, amplifying the prescore's own bias instead of correcting for it.
- **ParcelingInferrer** — approved population binned via `qcut` (equal-frequency), rejected population binned via `cut` (equal-width, over the *rejected* population's own score range) — two unrelated bin systems mapped onto each other by index, effectively assigning near-random bad rates.
- **Pipeline-level (`_train_and_evaluate_models`)** — `split_col` mode set `val = approved.copy()`, i.e. validation was literally the training population; every non-weighted method's `train_AUC` and `validation_AUC` came out identical to 6 decimal places, and GBM early stopping had no real holdout to stop against.
- **Continuous pseudo-labels got hard-binarized at `>0.5`** downstream in the pipeline, compounding whichever of the above was already wrong.
- **SimpleAugmentInferrer** hardcoded `np.random.seed(42)`, polluting the global RNG state and ignoring `cfg.random_state` (lower severity — the method is "assign the approved bad-rate at random" by design, so the direction bugs above don't apply to it, but reproducibility did).

**Fix:** `score_direction` parameter added to every inferrer + `ri_score_direction` (`"high_bad"`/`"high_good"`) on the pipeline config; `_default_hard_cutoff`'s percentile flips with direction; fuzzy rewritten to the textbook form (approved weight 1, rejected duplicated into weighted good/bad rows); parceling given shared `parcel_edges_`; `ri_validation_frac` added for a genuine holdout; SimpleAugment moved to an instance RNG.

**Durable lesson:** any score-consuming module needs its polarity convention pinned and checked against what's actually fed in. These bugs threw no exceptions — they just produced confidently-wrong, business-plausible-looking numbers (a "hard cutoff" method assigning rejects a *lower* bad rate reads as surprising but not obviously broken until you check the arithmetic).

## Weighted screening bugs (introduced 0.3.7, fixed 0.3.14)

- **Correlation silently blind to NaNs.** `_weighted_pearson_corr_matrix` ran `np.cov(..., aweights=w)` directly on raw (possibly-NaN) columns; any NaN anywhere in a column propagates `cov` to NaN, which then got `np.nan_to_num(nan=0.0)`'d — i.e. any feature pair where either column has missing values reads as *uncorrelated*, and both survive correlation dedup untouched. On this project's real feature matrices (20–35% NaN from cleaned sentinel values) this made the correlation stage close to a no-op for most pairs. Confirmed empirically with a synthetic 30%-NaN pair at true correlation ≈0.999: both columns survived pre-fix. The weighted path also ignored `corr_use_woe_bins` (the unweighted path respected it).
- **Silent "everything survives" fallback.** Every stage (PSI/IV/corr) used `current = keep or current` — if a threshold eliminated every remaining variable, the function quietly returned the untouched input set with no warning and no trace in the summary table.

**Fix (0.3.14):** `corr_nan_policy` (`"pairwise"` default — complete-case overlap per pair; `"median_fill"`; `"raise"`); weighted corr now also respects `corr_use_woe_bins`; `on_empty_stage` (`"keep_all_warn"` default — same fallback behavior, but now `warnings.warn`s and appends a `*_fallback` row to `.summary`; `"raise"` for strict use).

**Durable lesson:** a covariance/correlation computation over a real feature matrix needs an explicit NaN policy stated out loud — the numpy default ("propagate to NaN, then someone downstream coerces NaN to 0") is silently equivalent to "assume uncorrelated," which is the least safe possible default for a dedup step. Separately: any "keep everything" fallback is only a safety net if it's loud: a silent one is indistinguishable from "the filter worked."

## Mixed categorical + numeric IV screening KeyError (0.3.14, fixed 0.3.15)

- **Trigger:** `selection_enabled=True` + shared WOE bins (`iv_use_woe_bins=True`) + `categorical_features` passed to `MonotoneWOEBinner(cate_feats=...)` + at least one categorical feature survives IV cut alongside numeric features in the same `high_iv_varlist`.
- **Symptom:** `KeyError: "['MIN', 'MEAN', 'MAX'] not in index"` in `WOE_Engine_Feature_Patch._screening_summary_from_engine` (or the parallel path in `Feature_Insights.get_var_analysis_report`) when merging `proc_means_by_grp` output. Pure-numeric feature sets unaffected.
- **Root cause:** `proc_means_by_grp` melts numeric + object columns together; pandas `describe()` on the mixed melt returns `count/unique/top/freq` for object columns, not `MIN/MEAN/MAX`.
- **Fix (0.3.15):** `Distribution_Tool.proc_means_for_screening` splits by dtype before calling `proc_means_by_grp`; categorical rows get `min/mean/max` as NaN.

**Durable lesson:** any batch stats helper that assumes numeric `describe()` columns will break the moment categorical features share a melt with numerics — split by dtype or reindex defensively.

## RejectInferencePipeline weighted GBM training was a no-op (fixed 0.3.16)

- **Trigger:** any RI method that emits `_weight` (`fuzzy_augment`, `parceling`) with `train_ri_models=True`. Approved-only methods (`simple_augment`, `hard_cutoff`) are unaffected.
- **Symptom:** none — training succeeds, no warning, no error. Model output looks plausible. But the weighted rows have zero effect: swapping in any other weight vector (all-ones, random, business rebalance) trains an identical model to the true `_weight`.
- **Root cause (`Pipeline/reject_inference.py` L623 in 0.3.15):** `fit_kwargs = {"wgt": weight}` passed to `GradientBoostingModel.fit`. The fit signature is `(x, y, valx, valy, init_score=None, sample_weight=None, eval_sample_weight=None, sample_weight_eval_set=None, **kwargs)` — `wgt` is not a real parameter and is silently absorbed by `**kwargs` and dropped. `GradientBoostingModel` uses `sample_weight`. Old SMF versions did expose `wgt=` on LGB fits, but the API was unified to `sample_weight` in an earlier version and this pipeline site was never updated.
- **Fix (0.3.16):** `fit_kwargs = {"sample_weight": weight}`. Regression test `SuperModelingFactory_pytest/test_reject_inference_weighted.py` intercepts `GradientBoostingModel.fit` and asserts (a) `sample_weight` is in the observed kwargs, (b) `wgt` never is, (c) the vector length matches the train row count.

**Durable lesson:** any `**kwargs`-accepting fit / call site where a Pipeline hand-rolls the kwarg dict is a silent-drop trap when the underlying signature evolves. When SMF unifies a param name (as with `wgt` → `sample_weight`), grep every callsite in `Pipeline/*.py` at the same time, not just the `Model/*.py` definition — the compiler will not catch drift into `**kwargs`. `require_params(fit, "sample_weight")` in the pytest suite would catch this class of regression.

## Missing-rate screening stage gap (fixed 0.3.15)

- **Before 0.3.15:** `FeatureScreenConfig` and `FeatureValidationPipelineConfig` had no `missing_rate_threshold`; screening ran PSI → IV → corr only. `missing_rate` appeared in IV tables but was not a pre-PSI filter stage.
- **Fix (0.3.15):** `missing_rate_threshold: float | None = None` on both configs; when set, stage 0 runs on INS before PSI, drops features above threshold, persists `missing_rate_table` / `missing_rate_dropped` on `WeightedScreenResult` and FVP selection outputs.

## `apply_woe` O(n²) performance (fixed before 0.3.3)

`WOE_Monotone_Binner.apply_woe` inserted new WOE columns one at a time via `df[col] = ...`, each insertion forcing pandas to reallocate its internal block manager. On wide batches (100–250+ new columns per call) this dominated runtime and was the confirmed (via `py-spy` stack sampling of a live, stuck process) root cause of a 3,380-candidate-feature validation run blowing through a 12-hour cell timeout with 14/14 batches still not finished. Fixed by collecting the new columns and adding them via a single `pd.concat(axis=1)`.

**Durable lesson:** if a WOE/feature-assembly step scales worse than linear with column count, suspect column-by-column DataFrame mutation before suspecting the statistics.

## Persistence

- **Always load SMF-saved models via `Core.load_model(path, return_metadata=True)`.** A bare `pickle.load` on an SMF model artifact raises a confusing `No module named '1'`-shaped error — SMF wraps saved models in its own versioned container, not a plain pickle of the estimator.
- **`LRMaster` used to pickle its full training frame (`_data`)** — tens to hundreds of MB, and literally row-level customer data riding along inside a model artifact (a real governance issue, not just bloat). Fixed via `__getstate__`/`__setstate__` dropping `_data` on save. Consequence: `get_statsmodel_summary` / `get_aic` / `get_bic` called on a *loaded* model now require an explicit `data=` kwarg and raise a clear `ValueError` telling you so if you omit it — this is intentional, not a regression.
- **`CreditModelPipelineConfig` had no `save_models` field at all** before it was added — the `models/` output directory was created either way (dead giveaway that something's missing, not that nothing was supposed to be there) but stayed empty until the field landed.

## Evaluation-table labeling

- **`model_perf_compare`'s `sample_name` was hardcoded to `"oot"`** regardless of what population was actually being scored — every table it powers (including every one of `ScoreComparisonPipeline`'s global and group-by outputs) had its `index`/scope column mislabeled `"oot"` even for the full sample or an arbitrary subgroup. Fixed by adding an explicit `sample_name` parameter; `ScoreComparisonPipeline` now passes `"global"` at every internal call site, and the bare function's own default changed to the neutral `"all"`. If anything calls `model_perf_compare` directly without passing `sample_name`, its output labeling changed meaning across this version bump — check call sites, not just the pipeline.

## Explainability

- **Owen values deliberately skip `xgb`** — `_run_explainability`'s Owen branch is gated `name != "xgb"`. By design, not a bug; don't "fix" it without finding out why first.
- **LIME was fully hand-rolled through 0.3.6**, absorbed natively into `Explainability.Model_Explainer` (`lime_explain_instance`, `lime_global_importance`, with built-in missing-value handling) as of **0.3.13**. This is the concrete precedent for the escalation ladder in `SKILL.md`: a hand-built workaround (including its NaN-median-fill fix for the fact that raw/non-WOE features commonly contain NaNs, which vanilla LIME's sampler can't handle — `scipy.stats.truncnorm: scale must be positive`) can be quietly absorbed upstream. **Check `ModelExplainer` for a native method before hand-rolling an explainer again on any version ≥0.3.13.**
- **`explain_outputs` (the computed SHAP/Owen tables) may not be persisted to disk** even when an `explain/` output directory is created and `explain_models`/`owen_enabled` ran without error — the tables can live only in the in-memory `CreditModelPipelineResult` for that kernel's lifetime. If the kernel dies before you persist them yourself (a later cell crashing, an OOM, a LIME NaN blowup), they're gone; recover by reloading the saved model via `Core.load_model(..., return_metadata=True)` (for `feature_cols`/`feature_source`) and recomputing with the same `sample_n`/`background_n`/`random_state`. Check whether the installed version's `_run_explainability` calls a persistence helper (look for something like `persist_explain_outputs` in `Pipeline._common` actually being invoked, not just importable) before assuming this gap is still open.
- **Environment, not SMF:** a long stretch of this project ran with `explain_models=[]` as a standing workaround because the installed `numba` (0.56.4, compiled against numpy<1.24) was ABI-incompatible with the installed `numpy` (2.2.6) — `import shap` crashed transitively via numba. `_run_explainability` catches this per-model and returns `{"error": repr(exc)}` rather than failing the whole pipeline, which can look like "explainability isn't configured" rather than "the environment is broken" — if a model's `explain_outputs` entry has an `"error"` key, check the environment before the config. Working combination found: `numba==0.66.0` + `llvmlite==0.48.0` + `lime==0.2.0.1` + `scikit-image>=0.25` + `pywavelets>=1.8`, with numpy/shap/lightgbm/xgboost/catboost left untouched.

## Data hygiene that belongs *before* the SMF call, not inside one

Neither of these is an SMF bug — both are exactly the kind of requirement that feels like "I'll just hand-filter the DataFrame" until you check whether a Config field already covers it:

- **Negative sentinels in CDC feature/score columns** (`-1`, `-2`, `-100`, observed at ~35% of an entire feature matrix's cells by count) are not valid numeric values. SMF's binners will bin them as real numbers if you feed them in as-is — always `NaN` them first, and do it consistently for every column an evaluation touches (score columns included, not just model features).
- **A population that should be excluded from fitting but retained for evaluation** (this project's "FT" cohort — a natural-approval segment that bypasses normal model scoring) is handled by `woe_fit_query` (fit-time exclusion) + `extra_eval_datasets` (eval-only inclusion) on the relevant pipeline, once those fields exist on the installed version — check before hand-splitting the DataFrame yourself.

## Pipeline hardening batch (fixed 0.3.17)

Four independent HIGH-severity gaps found during a full re-read of the seven Pipeline modules on the 0.3.15 → 0.3.16 baseline, all shipped together in 0.3.17. None of them threw a loud exception before the fix; all four either produced silently-wrong outputs or reported an error a long way from the actual root cause.

- **H1 — `CreditModelPipeline._fit_models` mutated the user's `cfg.model_params["lr"]`** on the LR training branch. The old line was `lr = LRMaster(params=params or None, standardize=bool(params.pop("standardize", False)) if params else False)`; `params.pop("standardize", False)` ran on the *same* dict already passed to `LRMaster(...)` (via reference), and the truthiness short-circuit made the behavior further order-dependent. Symptom: user's config `{"standardize": True, ...}` had `"standardize"` disappear after `.run()`, breaking a second run or any downstream code that expected the field. Fix: copy first, pop second — same pattern the neighboring `_run_lr_search` already used at L901–902.
- **H2 — `oot_col == 0` silently routed every string-flag row to OOT.** Both `CreditModelPipeline._split_data` (L420–421 pre-fix) and `FeatureValidationPipeline._split_dataset` (L910–912 pre-fix) used `work[cfg.oot_col] == 0` / `!= 0`. If the column came in as `"0"`/`"1"` strings or `"train"`/`"test"` labels (common Hive/ODPS export artifact), the equality comparison against integer `0` was false for every row → `ins_oos` came out empty, `oot` swallowed the whole frame, no exception. Fix: shared `split_oot_by_flag` helper in `Pipeline/_common.py` runs `pd.to_numeric(..., errors="raise")` — numeric strings (`"0"`/`"1"`) still work, boolean flags still coerce, but non-numeric content now raises a clear `TypeError` at the split step instead of producing empty training data.
- **H3 — `RejectInferencePipeline` implicit prescore path was un-validated.** `_run` triggers prescore training either when `cfg.train_prescore=True` **or** when `cfg.score_col not in data.columns` (implicit path — no external score means we have to fit one). `_validate_input` only checked `target_col` presence on the first branch, so the second branch failed deep inside `_fit_prescore` with a positionally confusing `KeyError`. Fix: `_validate_input` now checks `cfg.train_prescore or cfg.score_col not in data.columns` up-front and raises with a message that includes both `train_prescore` and the `score_col` presence status.
- **H4 — `RejectInferencePipeline` `oot_frac + ri_validation_frac >= 1` silently leaked OOT into validation.** `_sample_validation_ids` builds `pool = approved[~approved["_smf_ri_row_id"].isin(exclude_ids)]`; when `exclude_ids` (OOT + prior selections) covered everything, `pool` was empty and the code fell back to `pool = approved.copy()` — meaning the "held-out" validation set was resampled from the full approved population, including the OOT rows. Metrics on validation and OOT then shared rows, quietly biasing the validation number toward OOT and invalidating any early-stopping decision that used it. Fix: `_validate_ri_approved_config` now enforces `oot_frac + ri_validation_frac < 1` and `oot_frac ∈ [0, 1)` at `run()` start; the fallback branch itself was left alone because the assertion makes it unreachable under any valid config.

**Durable lessons across all four:**
- Silent equality-based routing on an ambiguously-typed column (`work[col] == 0`) is a landmine any time the column might be a string/boolean; always coerce and validate at the boundary.
- "Fallback to full population" is only safe if it's loud — the RI validation fallback and the string-oot-flag routing both silently produced business-plausible-looking but wrong numbers.
- When one code path validates a precondition and a parallel path skips validation, the "unchecked" path is where the confusing error will surface — always check every branch that requires the precondition, not just the obvious one.

## Pipeline hygiene batch (fixed 0.3.18)

Three independent MEDIUM-severity gaps found in the same 0.3.15 → 0.3.17 review that produced the H1–H4 batch, held back for a follow-up release to keep 0.3.17 focused. None crashed loudly on the fix path; each either produced silently-wrong data, silently discarded user intent, or failed at a confusing point far from the real problem.

- **M2 — `CreditModelPipeline._fit_woe` copied `warm_start_score_col` with a bare `.to_numpy()` and no length guard.** Both the reused-from-screening branch (L600–606 pre-fix) and the fresh-fit branch (L697–704 pre-fix) did `df[cfg.warm_start_score_col] = splits[name][cfg.warm_start_score_col].to_numpy()` to copy the warm-start scores from raw splits into WOE-transformed splits. This relied on WOE transformation preserving the row count exactly; any upstream `.dropna()`, fit-query filter, or reindex on either side would silently corrupt the join — one frame's rows attached to another frame's scores, no error, no warning. Fix: new `Pipeline/_common.copy_column_length_checked(dst, src, col, dst_name, src_name)` helper enforces `len(dst) == len(src)` before the positional `.to_numpy()` copy and raises `ValueError` with both frame names if they've drifted. Both `_fit_woe` call sites and the `_reuse_screening_woe` helper now route every warm-start copy through it.
- **M3 — `RejectInferencePipeline._run` silently overwrote a user-supplied `cfg.score_col`.** The prescore path fires when `cfg.train_prescore=True` **or** when `cfg.score_col not in data.columns`. In the combined case (`train_prescore=True` *and* `score_col` already present in the input frame) `_fit_prescore` unconditionally wrote its own model's predictions into that column with no warning — the user's pre-supplied score column vanished with no trace. Fix: emit a `UserWarning` before calling `_fit_prescore` when the overwrite is about to happen, naming the column and both opt-outs (`train_prescore=False` to reuse, or rename `cfg.score_col` to sidestep the collision). Skipping the prescore fit was rejected because a user who explicitly set `train_prescore=True` *is* asking for a fresh fit — the bug is only that the collision was invisible, not that the overwrite was inherently wrong.
- **M4 — `_fit_prescore` fed an empty frame to `SampleSplitter.split_df`.** `approved = data[(approved_col==1) & target_col.notna()]` with no guard: if no approved rows had observed targets (mislabeled columns, an all-rejected batch, target-column contract mismatch), `SampleSplitter.split_df` failed deep inside sklearn with a confusing `stratify` error. Fix: `_fit_prescore` now raises a targeted `ValueError` when `len(approved) == 0` with counts of `approved` and `target-observed` rows plus the total row count — the message tells the caller whether they have an approved-count problem, a target-null problem, or both. Aligns with the H3 pattern of failing at input validation with diagnostics rather than deep in a downstream call.

**Durable lessons across all three:**
- A positional column copy (`.to_numpy()`, `.values`) is only safe if the length invariant is enforced explicitly — pandas won't error on a length mismatch because there is no length mismatch at that call, the mismatch is between the two frames being combined and pandas never sees them together.
- "Overwrite silently on collision" is a defensible default only when the collision itself is impossible; the moment two config paths (`train_prescore`, `score_col`) can both be set, the collision case needs a warning at minimum.
- Any deep-in-sklearn error a Pipeline can predict from its own preflight state should raise early with counts, not later with a stack trace pointing at library internals.

## Pipeline hygiene batch #2 (fixed 0.4.0)

Six independent MEDIUM-severity gaps across five Pipeline modules, shipped together. One of them (**M5**) is a behavior change that flips a default and forced the version bump from a 0.3.19 patch to a 0.4.0 minor. The other five are pure hardening — silent-failure closures, one performance rewrite, one preview API.

- **M1 — `CreditModelPipeline._run_optuna` fell back to defaults on empty `search_spaces={}`.** The old line was `search_spaces = cfg.optuna_params.get("search_spaces") or self._default_search_spaces()` — an explicit empty dict is falsy, so `or` swapped it out for the built-in default. Users passing `optuna_params={"search_spaces": {}}` to say "run no optuna search" got the default search anyway. Fix: `is None` check instead of truthiness. Untangling the same footgun in any newly written pipeline code is now cheap because the pattern is fresh.
- **M5 — `ScoreComparisonPipelineConfig.cross_vars` default flipped from `["rating"]` to `[]`.** The old default forced a `rating` column via `_validate_input` and crashed for the (majority) callers who don't have one. In 0.4.0 the default is `[]`, `_validate_input` no longer includes `cross_vars` in the required-columns list, and the run loop soft-skips any `cross_var` that isn't in the input frame with a `_logger.warning`. **Breaking change**: callers who relied on the implicit rating breakdown must now pass `cross_vars=["rating"]` explicitly. This is why the release is 0.4.0 rather than 0.3.19.
- **M6 — `ScoreConsistencyUATPipeline` silently coerced object columns to numeric.** `_load_dataframes` ran `pd.to_numeric(df[col], errors="coerce")` on every object column and swapped in the coerced version whenever `notna().any()`. Rating columns like `["A", "B", "1", "2"]` silently lost the alpha buckets to NaN. Fix: new `numeric_coercion_mode` config field with three modes (`"safe"` default = only coerce when ≥`numeric_coercion_min_ratio` of non-null values parse, warn otherwise; `"aggressive"` = old 0.3.x behavior but with a warning per lossy column; `"off"` = never coerce). To restore 0.3.x behavior explicitly: `numeric_coercion_mode="aggressive"`.
- **M7 — `FeatureValidationPipeline._split_frame` bare-except swallowed stratify failures.** `try: SampleSplitter(...).split_df(...) except Exception: pass` dropped every failure into a naive random split with no diagnostic. Fix: `except Exception as exc` + `_logger.warning` that includes `target`, `test_size`, `random_state`, and the repr of the exception. No behavior change to the fallback itself; only observability. Module now imports `logging` and defines `_logger = logging.getLogger(__name__)`.
- **M8 — `FeatureValidationPipeline._high_corr_pairs` was O(n²) Python with `.loc[]`.** The old nested loop did ~4.5M scalar `corr_matrix.loc[var1, var2]` lookups at 3000 features. Rewritten with `np.triu_indices(n, k=1)` to lift the upper triangle in one vectorized shot, `np.isfinite & (np.abs > threshold)` mask, then set-membership for `pair_type`. **Output is numerically identical** to the loop — verified by the regression test `test_pipeline_medium_0400.py::TestM8HighCorrPairsVectorized::test_matches_loop_reference` which keeps a copy of the loop as a numerical oracle. No behavior change, just faster.
- **M9 — `SampleAnalysisPipeline` silently spawned up to 960 splits by default.** Default `4 targets × 4 windows × 3 ratios × 20 seeds` grid × `SampleSplitter` per cell, no preview. Fix: new `dry_run: bool = False` config field short-circuits `run()` to skip all computation and only return an estimate dict in `split_candidate_summary`; new public method `estimate_split_count(data=None) -> dict` returns the grid product plus, when `data` is provided, `available_oot_periods` and `windows_usable`. Nothing in the default execution path changed — the preview is strictly opt-in.

**Durable lessons across the batch:**
- **`or` on a container defaults to non-empty**: `cfg.get("x") or default` treats a deliberate `{}` / `[]` / `""` the same as "unset." When a user's intent might be "explicitly empty," write `is None` instead. Applies to M1, but grep every Pipeline config-consumer for the same idiom before it lands again.
- **A default value that requires a column is a footgun, not a feature.** `cross_vars=["rating"]` (M5) is a two-liner in the config file that quietly costs a KeyError to every user without the specific rating column the author had in mind. Any list-typed config default should be `[]` unless the column is one SMF itself creates.
- **`pd.to_numeric(..., errors="coerce")` followed by a truthiness check is a silent lossy conversion.** M6's fix (opt-in mode + per-column loss warn) is the pattern to reach for any time an object column might contain a mix of parseable numbers and legitimate string labels.
- **`np.triu_indices` is the vectorization for anything shaped like a pair-loop over a symmetric matrix** (M8). If a Pipeline method has `for i, ...: for j in ... [i+1:]: matrix.loc[i, j]`, it's a candidate.
- **A grid-search default that multiplies to hundreds of runs needs a `dry_run` or `estimate_*` counterpart on the same config** (M9). Adding it as a public method (not just a private helper) keeps the escalation ladder from having to re-derive the same math on the caller side.

## Defensive hardening batch (fixed 0.4.1)

Three independent LOW-severity gaps across three modules. All three took a code path that could silently ship wrong or misleading numbers and made it loud — either raising an explicit error with an actionable message, or emitting a warning that names the model / column / count involved. No behavior change on healthy inputs.

- **L1 — `RejectInferencePipeline._default_hard_cutoff` returned NaN on all-NaN scores.** The old fallback `return float(approved[cfg.score_col].median())` silently returned NaN when every bad-sample score was NaN and the overall score column was also all-NaN. That NaN threaded into every downstream `score < cutoff` comparison in `HardCutoffInferrer`, producing an empty inferred rejected set with no signal at all. Fix: check `np.isfinite(fallback)` and `raise ValueError` with a message pointing at `ri_method_params['hard_cutoff']['cutoff']` when the median itself is NaN; emit a `RuntimeWarning` (naming `cfg.score_col` and the median value) when only bad-sample scores are NaN but the overall median is finite. Healthy path untouched.
- **L2 — `predict_positive` had no shape/length/finiteness contract.** The old code took `pred_arr[:, 1]` for 2-D `(N, ≥2)` and `pred_arr.reshape(-1)` for everything else. Silent failure modes: (1) 2-D `(N, 3+)` output from a stray model wrapper still went through `[:, 1]` with no warning; (2) any model whose `predict_proba` returned fewer rows than input (silent row drop inside `LRMaster` variants or custom wrappers) got broadcast into misaligned score columns downstream; (3) NaN/Inf predictions propagated silently. Fix: explicit branch for `ndim ∈ {1, 2}` with 2-D `shape[1] ∈ {1, 2}` accepted, everything else raises `ValueError`; explicit `len(result) == len(data)` assertion raises with the model class name on mismatch; NaN/Inf warn (RuntimeWarning) with count and model class. Sklearn `(N, 2)` and LRMaster 1-D paths both work as before, just with the assertions on top.
- **L3 — `_ivks_from_binner` mixed `Interval + NaN` groupby was pandas-version-dependent.** `adapter.assign_bins()` can return a mix of `pd.Interval` objects and `NaN` for the missing bin. The old `groupby("bin", dropna=False)` used `sort=True` implicitly — under pandas <2.0 that mixed-dtype key raised `TypeError: '<' not supported between instances of 'Interval' and 'float'`; under pandas ≥2.0 it worked but on an implementation detail. Fix: cast bins to `object` dtype, replace NaN with an explicit `"__MISSING__"` string sentinel via `np.where(pd.isna(bin_arr), "__MISSING__", bin_arr)`, and set `sort=False` on the `groupby`. Downstream `sort_values("bad_rate")` handles ordering anyway, so the reordering is invisible outside the intermediate frame. Numerically identical on healthy pandas ≥2.0.

**Durable lessons across the batch:**
- **Any `.median()` / `.mean()` / `.percentile()` used as a fallback needs a `np.isfinite` guard before returning.** Aggregation over all-NaN is a real thing (M1 style), and NaN propagating through downstream comparisons is invisible until the wrong result ships. The two-line pattern (`if not np.isfinite(x): raise ValueError(...)`) is cheap and belongs anywhere an aggregate is the escape hatch of a `len(...) == 0` branch.
- **Anywhere a model's `predict_proba` output becomes a DataFrame column, assert length equality with the input frame.** Row-drop-inside-a-model-wrapper is impossible to notice from the calling code because the model looks fine and the assignment doesn't error — but the join between the wrong-length score array and the input frame silently reindexes/broadcasts. `assert len(result) == len(data)` is the cheapest way to catch it and names the actual failure.
- **`groupby(..., dropna=False)` on a mixed-dtype key relies on implementation detail.** If NaN is one of the possible key values and everything else is a non-comparable object type (Interval, custom class, mixed), replace NaN with a sentinel of the *dominant* dtype and pass `sort=False`. Costs nothing on the healthy path and removes an entire class of version-dependent failures.
- **"LOW severity" here means the code path is rarely hit, not that the failure is minor when it is hit.** Every one of these produced silently wrong data on trigger — L1 empties an inferred set, L2 misaligns a score column, L3 masks an IV computation crash under old pandas. Ship them as defensive hygiene, not as "someday when there's time."

## HIGH hotfix batch (fixed 0.4.2)

Five independent HIGH-severity gaps found during a full re-read of 0.4.1 new code plus the non-Pipeline modules (`Core`, `Sample`, `Feature`, `Model`, `Eval`, `Explainability`). All five either produced silently-wrong outputs or corrupted persisted state without raising. Shipped together in 0.4.2 as a pure hardening release — no new features, no API additions beyond one new opt-in policy field on `PSI_Tool`.

- **N11 — `Core/ODPS_Tool.upload_df` was non-atomic: delete-then-recreate.** The old sequence was `o.delete_table(name, if_exists=True)` → `o.write_table(name, df)`. If the process died, ODPS quota-blocked, or the network dropped between the two calls, the target table was left dropped with no data — every reader of that table then failed with "table not found" until the next successful run. Downstream Pipeline monitoring jobs that read a rolling snapshot table were the observed victims. Fix: default `atomic=True` writes to a temp table `{name}__tmp_{uuid}` first, then `ALTER TABLE ... RENAME TO ...` swaps it in and drops the old one; on any exception mid-write the temp is cleaned up and the original table is left untouched. Legacy delete-then-recreate path preserved as `atomic=False` for callers who explicitly want the old behavior (rare — mostly test fixtures). No signature change beyond the new kwarg.

- **N16 — `Sample/Sample_Split.split_df` dropped `exclude_cols` from the output frames.** The old implementation ran `X = data.drop(columns=exclude_cols)` then split `X` — the returned train/test frames were missing every column the user had asked to exclude *from splitting*, not from the output. Users passing `exclude_cols=["user_id", "loan_date"]` to keep those columns out of the stratification key lost them entirely from the downstream training frame, and the failure was silent until a later step tried to read `user_id` back. Fix: split on index (`np.arange(len(data))` + sklearn's `train_test_split` on indices with the stratify vector), then `data.iloc[train_idx]` / `data.iloc[test_idx]` — both output frames retain **every** column including `exclude_cols`. `exclude_cols` now only governs what participates in the split criteria, matching the user-facing contract in the docstring.

- **N17 — `Sample/Reject_Infer.HardCutoffInferrer.infer` propagated NaN scores as inferred labels.** The old `rejected_scored["target"] = (rejected_scored[score_col] < cutoff).astype(int)` treated NaN < cutoff as False and assigned `target=0` to every reject with a missing score. In the observed failure, a stray model wrapper dropped ~4% of reject rows to NaN scores; those 4% then joined the training frame as confidently-good synthetic labels, biasing the next-cycle model toward approving them. Fix: `np.isnan(rejected_scored[score_col]).all()` raises `ValueError` with a message pointing at the prescore column; partial NaN emits a `RuntimeWarning` (naming `score_col` and the NaN count) and assigns `target=NaN` (float dtype) to those rows so downstream `.dropna(subset=["target"])` filters them out cleanly instead of silently mislabeling them. Added `import warnings` at the top of the module.

- **N23 — `Feature/Weighted_Screen._weighted_bin_distribution` force-unioned a missing bin sentinel and clipped negative weight totals.** The old code took every fitted bin plus a hard-coded `_MISSING_BIN` string and computed `np.clip(bin_weight_sum, 0, None)` on the sample-weight aggregate. Two failure modes: (1) when the input frame had no missing values, the returned distribution still contained a zero-count `_MISSING_BIN` row, inflating the bin count reported by every downstream PSI/IV consumer by exactly one and shifting the distribution's normalization; (2) the `clip(..., 0, None)` silently absorbed negative-weight sums (a real error signal for wrongly-signed IPTW weights) instead of raising. Fix: `_weighted_bin_distribution` returns observed-only bins — no `_MISSING_BIN` union unless a NaN is actually present in the source column — and drops the `clip` entirely. Negative weight sums now propagate as-is; the caller's downstream `assert (weights >= 0).all()` at the entry to `weighted_feature_screen` (added in 0.3.7, retained) catches them at the boundary with a clearer message. `content` kwarg kept for signature stability even though it no longer branches internal logic.

- **N29 — `Feature/PSI_Tool._calculate_single_psi` silently dropped the missing bin from both distributions.** The old implementation ran `.dropna()` on both the expected and actual bin-share Series before the PSI formula. Consequence: any drift in the **missingness rate itself** was invisible. A production example from the 0.4.1 audit: expected 5% missing, actual 30% missing, all observed bins otherwise stable → old PSI = 0.007 ("no drift"), correct PSI = 0.53 ("severe drift"). Fix: new config parameter `missing_policy: Literal["drop", "include", "warn_and_drop"] = "drop"` on `PSI_Tool.__init__` and `calculate_psi` — **default kept at `"drop"` for exact numeric backward-compat** with 0.4.1 and earlier. `"include"` keeps the `__MISSING__` bin in both distributions and includes its share in the PSI sum (the correct behavior). `"warn_and_drop"` matches old numeric behavior but emits a `UserWarning` naming the column and the difference in missing rates when either side has non-zero missing share. Module now defines `_MISSING_BIN = "__MISSING__"` as a top-level constant shared with `Weighted_Screen` for consistency. **The next minor release will flip the default to `"include"`** — noted in `changes_042.md` — following the same 0.3.19→0.4.0 pattern that flipped `ScoreComparisonPipelineConfig.cross_vars`.

**Durable lessons across the batch:**
- **A two-step "delete then recreate" against remote state is not atomic and needs an explicit temp-swap or transactional wrapper** (N11). Grep for `.delete_table(...)` / `.drop_table(...)` immediately followed by a `.write_...` / `.create_...` in every Core/IO module — that pattern is unsafe by default. `atomic_swap_table` / `atomic_swap_partition` are the utilities to reach for.
- **A column marked "exclude from computation X" must not disappear from the output of X** (N16). The user-facing name of the parameter tells you the contract; if the implementation ends up doing more than that contract says, the extra behavior is a silent bug even if the tests pass.
- **NaN comparisons default to False, so `(col < threshold).astype(int)` silently assigns 0 to every NaN row** (N17). Any boolean-cast-to-int of a comparison involving a column that might be NaN needs either an explicit `.notna()` mask or a NaN-target assignment; the "which one?" depends on whether the caller wants the rows silently included as False or filtered out downstream — but "silently False" is virtually never the right answer for a scored population.
- **`np.clip(..., 0, None)` on an aggregate that should never be negative silently absorbs the error signal** (N23). If the value going into `clip` is impossible-under-correct-input, clip is not defensive — it's a bug-hider. Prefer an assertion at the boundary where the invariant is guaranteed (the entry to `weighted_feature_screen`) and let the internal aggregate propagate whatever the math produces.
- **`.dropna()` on a distribution before a divergence metric silently discards the missingness dimension of the drift** (N29). Missing-rate drift is real drift; the tooling either has to include the missing bin in the metric or has to warn the caller that it's being dropped. Never silently drop.
- **When a fix changes numbers, ship it behind a flag with the old default, document the intended flip, and flip on the next minor release** — the 0.3.19→0.4.0 `cross_vars` pattern is now the standard for any behavior-changing default in this codebase. `missing_policy="drop"` is 0.4.2's version of the same pattern.

## MEDIUM batch (fixed 0.5.0)

Two MEDIUM-severity items shipped together in 0.5.0 as a coordinated correctness release. Both change observable numeric/logging behavior relative to 0.4.x; both are noted in `docs/changelog/v0.5.0.md` with migration guidance.

- **N29 — `missing_policy="drop"` default was left in place across the 0.4.x line and was still hiding missing-rate drift.** In 0.4.2 the `missing_policy` kwarg was introduced on `PSI_Tool.__init__` / `calculate_psi` with the intended flip to `"include"` on the next minor release, following the 0.3.19→0.4.0 `cross_vars` pattern. 0.5.0 completes that flip and simultaneously widens the API surface: the kwarg is now accepted (and forwarded internally) on **seven surfaces** — module-level `calculate_psi`, `calculate_psi_over_time`, `psi_report`, `plot_psi_trend`, `compare_distributions`, plus `PSICalculator.__init__` and `PSICalculator.calculate`. All seven default to `"include"`. Internal helper `_calculate_single_psi` default was also flipped from `"drop"` to `"include"` so any caller that reached the helper directly gets the corrected behavior too. Concrete numeric impact on the audit fixture (5% expected NaN → 30% actual NaN, all observed bins otherwise stable): PSI ≈ **0.0009 under the old default → 0.525 under 0.5.0**. Callers that need bit-exact continuity with 0.4.x reporting must pass `missing_policy="drop"` explicitly at every call site — the module-level constant `_MISSING_BIN = "__MISSING__"` continues to name the synthetic bin used by the include path. Sample-weighted PSI (`Weighted_Screen`) already used the include-style path since 0.3.14 and is unchanged; only unweighted `PSI_Tool` surfaces flip.

- **N38 — `WOE_Monotone_Binner.apply_woe` silently mapped unseen categorical levels to the training-time missing-value WOE.** The old code, on encountering a category present in the transform frame but absent from the fitted `value_map`, fell through to the same branch as `NaN` and assigned the fitted `nan_woe`. Two independent failure modes: (1) rare-category drift (a value that appeared only in OOT or in production) received a WOE that was fitted for a **structurally different** population — the missing subgroup — with no signal in the logs; (2) users who had already routed missing values through `unseen_category_policy` semantics in adjacent tools (e.g. sample-weighted screening) had no way to force an error or a distinguishable output for genuinely-new levels. Fix: `apply_woe` gained `unseen_category_policy: Literal["warn", "error", "silent"] = "warn"`. On any transform call where a categorical column contains a level not in the fitted `value_map`, the binner (a) records a per-column entry in `self._unseen_category_stats` — a `Dict[str, dict]` reset to `{}` at every `apply_woe` invocation, populated with `{"unseen_levels": [...], "unseen_count": int, "unseen_share": float}` — and (b) either emits a `RuntimeWarning` naming the column, levels, count and share (`"warn"`, default), raises `ValueError` with the same details (`"error"`), or does nothing user-visible while still populating the stats dict (`"silent"`). The mapped WOE value for unseen levels is still `nan_woe` — the fix is *observability + opt-in-strictness*, not a new imputation. Only the categorical branch (`vr.get("is_categorical") is True`) runs the detection; numeric bins are unaffected because unseen numeric values already fall into an existing bin range or trigger the missing bin explicitly. `warnings` was already imported at module top so no new import.

**Durable lessons across the batch:**
- **A shipped-with-old-default flag with an announced flip must actually flip on the next minor release** (N29). Leaving `missing_policy="drop"` in place across two minor bumps would have quietly re-established the original silently-wrong default as the codebase's steady state. The `changes_042.md` line "the next minor release will flip the default" is now a promise the codebase kept; the pattern only works if the flip happens.
- **Every module-level convenience wrapper around a class-based API is a place the kwarg has to be re-plumbed** (N29 API surface expansion). `PSI_Tool` shipped `missing_policy` on `PSICalculator.__init__` in 0.4.2 but the six module-level functions (`calculate_psi`, `calculate_psi_over_time`, `psi_report`, `plot_psi_trend`, `compare_distributions`, and internally `_calculate_single_psi`) did not accept or forward it. Users reaching for the module-level API — the documented entry point — got the old default even in 0.4.2. Whenever a new kwarg is added to a class method, grep the same module for `def ` at column 0 and audit whether each top-level function needs the same kwarg forwarded.
- **Silently mapping unseen categorical levels onto the missing-value bucket conflates two distinct populations** (N38). "Missing at training time" and "present in production but never seen at training time" are different subgroups with different risk profiles. Any WOE-style transform must expose *at minimum* an observability hook (the `_unseen_category_stats` dict) even if the default action stays soft (warn). Users who care can escalate to `"error"`; users who don't can still read the stats dict downstream and log a monitoring metric.
- **`-W error::RuntimeWarning` in a user's pytest config will now break `apply_woe` on any dataset with unseen categoricals** (N38 downstream trap). This is the single most likely 0.5.0 upgrade break for engineering teams who treat all warnings as errors. The migration answer is `unseen_category_policy="silent"` at the call site (or `warnings.catch_warnings()` around the call); both preserve the stats dict for offline monitoring. Documented in `v0.5.0.md` migration section.
- **PSI numeric values are not comparable across the 0.4.x → 0.5.0 boundary on any dataset with drifting missingness** (N29 downstream trap). Historical PSI reports stored from 0.4.x will look artificially calm compared to fresh 0.5.0 runs on the same data; teams that alert on absolute PSI thresholds (e.g. `psi > 0.25`) need to either re-baseline against a 0.5.0 recomputation or pass `missing_policy="drop"` explicitly to freeze the old numbers for continuity. Recommended: re-baseline. The old numbers were wrong.

## Feature / WOE hygiene batch (fixed 0.5.1)

Eight medium-severity hygiene issues shipped together in 0.5.1. Most were not crashers; they were silent numeric distortions or "where did my variable go?" diagnostics gaps.

- **Weighted IV zero-mass bins** used to let zero bad/good mass bins produce `inf` / `nan`, and the synthetic missing bucket could inflate predictive IV. Fixed by excluding the missing bucket by default and skipping class-degenerate bins with a warning.
- **`_assign_bins(edges=None)`** used to map every non-null value to `"all"` and produce IV=0. Fixed by raising a clear `ValueError` by default; `on_null_edges="warn_and_zero"` preserves the old permissive behavior explicitly.
- **`Feature_Screen` after missing-rate drop** used to refit later stages on the original feature list in some paths. Fixed so WOE / PSI / IV only receive the current surviving feature list.
- **PSI one-sided buckets** used to floor the absent side to `1e-6`, creating huge PSI spikes for small new-bucket mass. Fixed with `psi_missing_bucket_policy="smooth_laplace"` by default; `"floor_1e6"` is the old report-compatible path and `"exclude"` removes one-sided buckets from the sum.
- **Feature insight failures** in `Feature_Insights` and the WOE-engine patch used to disappear through broad or silent exception handling. Fixed by exposing `failed_variables` and emitting a single warning for expected per-variable failures; unexpected exceptions should propagate.
- **`WOE_Master` missing sentinel** default changed from `-999999` to `SMF_MISSING_BIN`. Passing finite sentinels now warns, and real collision in training data raises.
- **Empty WOE mapping tables** now raise a contextual `WOE_Master.woe_dict is empty` error instead of raw `No objects to concatenate`.

**Durable lesson:** feature-screening tools need loud failure surfaces. "Variable disappeared" and "metric is exactly zero" are often swallowed upstream exceptions, not clean statistical conclusions. Check `failed_variables`, sentinel collisions, and PSI bucket policy before trusting a calm report.

## Test-environment baseline (post-0.5.0)

Not a code bug — a **coverage-hiding gap** discovered while validating 0.5.0 in a fresh sandbox venv. Recorded here because the failure mode is silent (green run, 22 SKIPPED) and easy to miss on future releases.

- **`pytest --tb=short -q` reporting `N passed, 22 skipped, 0 failed` on a fresh SMF pytest venv is the default state, not a healthy state.** The suite covers three optional SMF capabilities — ODPS I/O (`odps` namespace), SHAP explainability, LIME explainability — that the main wheel deliberately does **not** declare as runtime dependencies. **Durable lesson:**
- **A green pytest run with non-zero SKIPPED count is a monitoring failure, not a success.** Every SKIP has to trace to either a documented `@pytest.mark.skip(reason=...)` or a missing optional import; the second category is a **coverage gap**, not an environment quirk. Treat any new `SKIPPED [could not import 'X']` line during release verification as a blocking finding and either (a) add `X` to `requirements-dev.txt` or (b) mark the test with an explicit reason that survives grep. 0-skip is the correctness baseline for this codebase from 0.5.0 forward.

## 0.5.6 retest residuals (fixed after 0.5.6, in the next release)

The 2026-07-12 full retest (TEST_REPORT, section 0.3) left two residuals; both fixed together after 0.5.6.

- **F3-residual — weighted shared-WOE-bins screen crashed on declared categorical features at the IV stage.** `Feature_Screen._weighted_woe_bins_screen`'s iv_enabled block ran `ins[var].to_numpy(dtype=float)` on every feature; string levels (e.g. `'4.high_school'`) raised `ValueError: could not convert string to float`. The cast's only consumer is `np.isfinite(x)` inside `_weighted_iv_from_assigned_bins` (weighted missing rate) — IV itself comes from the assigned bins. Fix: non-numeric columns now pass an observed→1.0/missing→NaN float proxy (notna semantics, matching `_missing_rate_for_series`); numeric columns unchanged. **The crash would otherwise just have moved one stage later:** with `corr_use_woe_bins=False` (the default) the raw-value corr stage ran `ins[current].astype(float)` on the same features — `_weighted_corr_for_screen` now computes the numeric sub-matrix under the user's `corr_nan_policy` and embeds it into a full-size NaN matrix (categoricals warned + kept, never dedup-dropped). Also wired `categorical_features` through `FeatureValidationPipeline._build_selection_config` so a selection run that fits its own screening binner (no prefit WOE engine) declares them properly.

Workarounds: pass a weight column, or `corr_enabled=False`, or exclude categoricals. Fix belongs in `CorrelationFilter`/`var_corr_filter` (shared primitives) — scoped out of the residual fix on purpose.
- **F4-residual — RI lr chain was unusable on real (NaN-bearing) features.** `reject_inference._fit_pipeline_model`'s lr branch fed raw features to `LRMaster` → sklearn `Input X contains NaN`. Fix: new `RejectInferencePipelineConfig.lr_nan_handling` (`"fillna_median"` default / `"fillna_mean"` / `"fillna_0"` / `"raise"`), vocabulary aligned with `LRM_Tool._prepare_nan_handled_frame` (`drop_rows` deliberately excluded — it would break `predict_positive`'s length contract). Fill values are computed **on the training frame only** (±inf treated as missing; all-NaN columns fall back to 0.0), applied to train/val with a loud `UserWarning`, and ride with the model via a module-level `_LRNanFillWrapper` that re-applies them at every predict call — train and scoring can never drift onto different imputations. The wrapper blocks dunder delegation so pickle serializes it (not the inner LRMaster's `__getstate__`), and `_save_pipeline_model` persists `lr_nan_handling` + `lr_fill_values` in the artifact metadata. **New finding (open, high leverage): module-level `warnings.filterwarnings("ignore")` in `Model/Backward_Tool.py:41` and `WOE/WOE_Monotone_Binner.py:63`.** These execute at (lazy) import time and wipe every active warning filter for the whole session — silently defeating the entire loud-failure program (0.4.x/0.5.x UserWarnings/RuntimeWarnings: N17, M3, L1/L2, N38, the new lr fill warning, all of them) for any user whose session imports either module, i.e. practically every real notebook. Discovered because a `warnings.catch_warnings(record=True)` block around a pipeline run recorded **zero** warnings: the lazy `from Modeling_Tool import LRMaster` mid-run re-triggered the module import and nuked the recording filters. Tests must pre-import these modules before any `pytest.warns` block. Proper fix (own pass, behavior change): scope the suppression to the specific noisy warnings or a `catch_warnings` context inside the offending functions.

**Durable lessons:**
- When a fix lets a previously-crashing input travel further down a staged pipeline, audit every later stage for the same assumption — "fixed at IV" would have just relocated the crash to corr.
- Any imputation applied at fit time must be captured as state and re-applied at predict time; filling only the training frame is a train/serve skew bug wearing a fix's clothes.
- A module-level blanket `filterwarnings("ignore")` anywhere in a library silently disables every carefully-designed warning everywhere else in it.

## Silent equal_freq WOE plot failure (fixed 0.6.2)

`FeatureValidationPipeline(woe_engine="equal_freq", plot_outputs=True)` silently produced **zero PNGs** under `figs/woe/` on every 0.5.x / 0.6.0 / 0.6.1 release, with no log line and no exception surfaced to the user. Two independent defects layered on top of each other:

- **API-surface defect (WOE_Master)**: `WOE_Master.plot_bivar_graph(self, data, group, dirname, varlist=None)` declared `group` as a **required positional argument**, even though the underlying primitive `get_bivar_graph(..., group=None, ...)` has always accepted an ungrouped call. `feature_validation._plot_woe` invoked it as `engine.plot_bivar_graph(transformed, dirname=str(base_dir))` — no `group` — for the base (ungrouped) figure, and got a `TypeError: missing 1 required positional argument: 'group'` on the very first call.
- **Silencer defect (feature_validation)**: the entire `_plot_woe` body was `try: ... except Exception: return`. The `TypeError` above was swallowed with **no log, no warning, no re-raise**. The monotone engine uses a different code path (`engine.plot_woe_graph`), so the blind spot only manifested on `equal_freq` and any other engine whose plot entry point is `plot_bivar_graph`. It survived from 0.5.x through 0.6.1 because the existing plot tests only covered the monotone branch and the equal_freq branch through `CreditModelPipeline`, whose call site correctly passed `group=` as a kwarg.
- **Secondary directory defect surfaced during the fix**: `WOE_Master.plot_bivar_graph` did not `mkdir` its composed `save_dir`. Callers were expected to pre-create every subdirectory; `feature_validation._plot_woe` only created the base `figs/woe/<target>`, so even after the `TypeError` was fixed the first PNG write would `FileNotFoundError`. Fix moved `os.makedirs(save_dir, exist_ok=True)` into `plot_bivar_graph` itself — the method that composes the path also owns creating it.

Fix (0.6.2):
- `WOE_Master.plot_bivar_graph` — `group` defaults to `None`; positional order preserved (`data, group, dirname, varlist`) for backward compatibility; `dirname=None` now raises a clear `TypeError` at call time; the method owns its `mkdir`.
- `feature_validation._plot_woe` — passes `group=None` explicitly at the ungrouped call site; the outer `except Exception:` block now emits a `_logger.warning` naming engine, target, output_dir, and the underlying exception, then returns. Plot failure still does not kill the pipeline, but it is no longer invisible.
- New regression coverage (`SuperModelingFactory_pytest/test_pipeline_bugfix_062.py`): API-surface (TestN45), end-to-end equal_freq PNG output through FeatureValidationPipeline (TestN46), and a logger-warning assertion for engine-side plot failures (TestN47).

**Durable lessons:**
- **A bare `except Exception: return` in a library is a bug in itself**, independent of any specific defect it hides. Every silenced exception is a monitoring failure waiting to happen. The canonical pattern in SMF from 0.6.2 forward: `except Exception as exc: _logger.warning("...error=%r", ..., exc); return` — log first, decide the recovery second. Silent failure is *more* dangerous than a crash because a crash gets fixed by the next release; a silent failure accumulates for years.
- **When you add coverage for a new configuration surface (like `plot_outputs`), sweep every engine/adapter path that flows through the same output block.** The 0.6.1 `plot_outputs` toggle was fully tested on the monotone engine and never exercised the equal_freq branch end-to-end — because the equal_freq path had been silently broken all along, no baseline existed to compare against. Grep for every branch of every `hasattr` / `get_engine_name()` switch and put at least one end-to-end assertion behind each.
- **Any method that composes a path should own creating it** (`os.makedirs(..., exist_ok=True)`). Splitting the responsibility between caller and callee (caller creates base, callee expects subdirs to exist) is a bug pattern that survives every refactor because it only fails on the third-least-common call site.

## equal_freq WOE plot close-out (fixed 0.6.3)

0.6.2 only fixed **half** of the silent-plot problem above. The 0.6.2 diagnosis included this sentence, which turned out to be wrong:

> "The underlying `get_bivar_graph` primitive has always accepted `group=None`."

It hadn't. The signature default was there, but the function body's `if group:` guard sat **after** the crash point. `get_bivar_graph` did the reference-WOE plot loop first (which writes PNGs successfully), then unconditionally called `get_mapped_woe_summary(..., grp_name=[group])` and `align_bin_num(..., grp_name=[group])` — those internally do `data.groupby([None])`, which raises `TypeError: 'NoneType' object is not callable`. Only after that unreachable code did `if group:` gate the plotting loop.

Net effect on 0.6.2 in the field:

| engine       | base PNGs                              | `by_<group>/*.png` | plot exception          |
|--------------|----------------------------------------|--------------------|-------------------------|
| monotone     | 6                                      | 3                  | none                    |
| equal_freq   | 3 (ref-plot loop runs before ② crashes) | **0**              | **TypeError** every run |

Because the 0.6.2 pipeline `try` block caught the `TypeError` and `return`ed, the subsequent `for group in cfg.woe_plot_groups:` loop that emits `by_<group>/*.png` never ran. The 0.6.2 `logger.warning` fix made the residual crash visible — that's how the second half was actually caught.

Fix (0.6.3): hoist `if group:` in `WOE_Plot_Tool.get_bivar_graph` so it wraps the `summary + align + plot` triplet. Docstring in `WOE_Master.plot_bivar_graph` corrected to remove the 0.6.2 wrong-assumption sentence.

Regression coverage (`SuperModelingFactory_pytest/test_pipeline_bugfix_063.py`): TestN46b (base plots emit no `WOE plot generation failed` warning), TestN48 (equal_freq + `woe_plot_groups=['chan']` produces `by_chan/*.png`), TestN49 (white-box: `get_bivar_graph(group=None)` does not raise).

**Durable lessons (three, all sharing one root cause):**

- **Signature defaults are not proof the body handles the default value.** Both the 0.6.1 and 0.6.2 wrong-turns came from reading `def get_bivar_graph(..., group=None, ...)` and stopping there. When the diagnosis hinges on "the underlying primitive supports X", read the body to the point where X is actually consumed — or write a white-box test that pins the claim.
- **"Output exists" ≠ "no error occurred."** The 0.6.2 D5 test asserted "PNG count > 0" and passed on 0.6.2 while every run also raised — because loop ① wrote PNGs *before* loop ② crashed. Any test path where the failure is caught by a surrounding `try/except` must assert **both** (a) the presence of the desired artifact and (b) the absence of warnings/exceptions from the operation. This is now `TestN46b`'s job: PNGs exist AND `caplog` shows no `"WOE plot generation failed"` warning.
- **The 0.6.2 `logger.warning` justified itself on day one.** It was the visibility half of a two-part fix; even though the behavioral half was wrong, the visibility half was what surfaced the residual crash for 0.6.3. When a bug has a visibility layer and a behavioral layer, always ship the visibility layer even if you're not 100% sure the behavioral layer is complete — you'll find out from the next crash.

## OOT governance gaps (found in the 0.6.4 audit, fixed after 0.6.4)

- A sentinel exception class (`BinningPolicyViolation`) is the clean way to make governance raises pierce blanket per-item fault tolerance — rewriting the blanket except would change failure semantics for every non-governance error.
- Serial/parallel drift dies at the source: extract ONE per-item core function and have both the serial loop and the chunk worker call it (`_dtree_refine_one_core`); resolving governance state before `copy.copy(self)` makes workers inherit it for free.

- Evidence for selection gates must be lazily priced on the survivor set (closures), not precomputed on the full feature list — grouped IV on 3000 features × 12 months is real money; post-corr survivors are typically 10× smaller.
- Optional-extra guards belong BEFORE any mutation at the gate entry, and the error must name the pip extra verbatim (`pip install "SuperModelingFactory[stats]"`).

## Weighted-path audit closure (found in CDC field use after 0.6.7, fixed 0.6.8)

The third and (for the screening layer) final round of weighted-vs-unweighted semantic divergence, after G16 (0.6.6, training weights leaking into evaluation) and the weighted screening bugs of 0.3.7→0.3.14. Field trigger: an FT-weighted CDC run where `iv_upper_threshold` failed to drop a hard leak feature that the unweighted monotone-engine run caught at IV≈24.

- **G02 upper band missed hard leaks on 3 of 4 dispatch paths.** Not a gate-wiring bug — all four paths called `_iv_band_keep` — but an IV-basis bug: the weighted IV's `iv_guard` excludes class-degenerate bins from the sum, and a hard leak makes bins class-PURE, so the strongest possible signal contributed *nothing* (measured 0.6–1.7 for a true-IV≈12 leak; fully-pure features measured 0.0). The legacy gains-table path zeroes pure bins the same way via `filliv`. Only monotone-engine report IV (zero-cell floored) was immune. **The 0.6.7 batch's own G02 tests were green because their `f_leak = y*2 + N(0,0.55)` is a SOFT leak — distributions overlap, no bin is pure, the degenerate regime was never exercised.** Fix: `_weighted_iv_detail` computes a zero-cell-FLOORED IV (shares floored at `content`, the PSI floor) in the same pass; every path gates the upper band on it; drops record `metric=iv_floored`. Reported IV columns stay legacy; `upper=None` computes nothing.
- **G03/G04 evidence chain ignored `weight_col` entirely.** Per-group IVs, per-target IVs, point-biserial directions — all unweighted even on weighted runs, so group-stability and multi-target decisions used a basis that does not match the modeling weights. Weights can flip every one of the three gate checks (verified constructions: monthly IV 4.6→0.2, per-target IV 2.2→0.01, direction +1→−1 in 2 of 3 months). Fix: `_evidence_iv` + `point_biserial_direction` gained `sample_weight`; `_build_selection_evidence` resolves `weight_col` once on INS (AFTER the gates-off early return, so gate-less weighted runs stay byte-identical) and re-slices positionally per group/target. `n` stays a RAW row count (weights add no statistical sufficiency); snapshot records `evidence_weight_col`.
- **Corrected diagnosis from the 0.6.7 commit message:** the G03/G04 evidence IV never had the `iv_guard` pure-bin hole — it uses the `+1e-6` additively-smoothed report formula where pure bins contribute large finite terms. The `iv_guard` hole's real landing spot inside the gates was `gate_iv_map` feeding **G05 truncation ranking and the G06 VIF tie-break**: legit features with class-pure bins ranked artificially low (guarded 0.2–0.5 vs floored ≈4) and got truncated in favor of weaker features. Fix: `_gate_ranking_iv_map` substitutes finite floored IVs for ranking ONLY when the upper band is armed (leaks already dropped by the band); unarmed keeps each path's legacy basis verbatim — deliberately, because floored ranking without the band would rank an uncaught leak first.

**Durable lessons:**
- Degenerate-bin exclusion inverts exactly for leak detection: a guard built to keep noise out of a LOWER informativeness bound silently zeroes the strongest features at the UPPER bound. Any IV consumer must pick its basis per purpose — guarded for floors, floored for leak ceilings, and ranking follows whichever hazard is already handled.
- Leak-detection tests need HARD leaks (class-pure bins, e.g. 80% separated mass + 20% mixed remainder so the suppressed IV lands innocently inside the band) — soft leaks with overlapping distributions never enter the degenerate regime and prove nothing about it.
- "Does this stage honor `weight_col`?" must be asked of every evidence/diagnostic computation SEPARATELY from the main stage math — this is the third time a side channel (evaluation weights, band diagnostics, gate evidence) silently stayed unweighted after the main path was weighted. The unit-weight parity test (`w=1.0` frame-equal to unweighted, bit-exact via bincount identity) is the cheap permanent guard; write it whenever a weight parameter is added.
- Weighted-vs-unweighted flip fixtures want frequency-scale weight contrast (1.0 vs 1e-3) on engineered signal rows, not random weights — each check (IV floor, IV range, direction consistency) gets its own weight column so one frame calibrates all flips deterministically.
- When a fix's ranking/ordering side effect could resurrect a hazard the legacy behavior accidentally suppressed (guarded ranking buried leaks at the bottom), condition the new behavior on the hazard's dedicated control being armed instead of changing the default.

## Categorical transform silent-mismatch family (G18; CDC field report investigated 2026-07-17, fixed after 0.6.8)

Field report: after upgrading to 0.6.8, a CDC equivalence rerun claimed native CMP lost ~1.6pp OOS AUC whenever one high-cardinality categorical feature (`addr_estado_main`, one "N=2, 100% bad, WOE=5.04" bin) entered the LR — with 0.6.4 and a hand-rolled sklearn LR on "the same WOE table" both healthy. The report's own root-cause hypothesis (0.6.8 CMP scaling/dummy-expanding categorical WOE before LR) is **false**:

- **Requalification verdict.** The 0.6.4→0.6.8 categorical→LR chain has zero behavioral diff: `_train_models` LR params are user params verbatim (`_DEFAULT_MODEL_PARAMS["lr"] == {}`), `LRMaster.fit → lr_model` is a transparent sklearn passthrough, and on both synthetic and real data the native design matrix equals the table mapping row-for-row while native LR coefficients equal a same-matrix sklearn refit bit-for-bit (verified across from_artifact-reuse / self-fit entries × legacy / candidate-mode-governed params — all four cells byte-identical). "Same table ⇒ same matrix" held everywhere a healthy column was fed.
- **What the field data actually contained.** The rerun-era `_optcache/train.parquet` had `addr_estado_main` as float32 with 43,248/43,250 rows NaN and exactly 2 surviving rows of value 1.0, both bad — the report's phantom "N=2 pure-bad bin" verbatim. The upstream prep had destroyed the column; SMF transformed it without a meaningful sound: 99.99% of rows silently took the [Missing]-bin WOE and the N38 unseen warning read "2/24716 rows (0.0%) affected" — technically true, diagnostically useless. A WOE **table** diff can stay bit-identical through all of this (the reused artifact carries the fit-time table), which is exactly why the reporter's equivalence check passed while the matrix was garbage.
- **Real defects fixed under G18** (all observational; mapped WOE values stay byte-identical):
  - `apply_woe` records `_categorical_transform_stats[feat]` = {total/missing rows, missing_rate, fit_missing_rate (from the fitted table + sv_table), exact/str-fallback/unmatched match counts} per call.
  - Missing-rate drift guard: transform missing_rate ≥ 50% while ≥ 30pp above fit-time → RuntimeWarning naming both rates ("column likely broken/renamed/re-typed") — the exact CDC shape.
  - str()-fallback guard: any row matched only by the `str(value)` fallback → RuntimeWarning (fit/transform dtype drift; the fallback can silently MIS-map when renderings collide — int 1 → "1" never matches zero-padded "01", and int/str MIXED columns mis-map with no unseen warning at all because every rendering is "seen").
  - CMP `_fit_woe` monotone self-fit now splits init-vs-fit kwargs like `fit_screening_woe_engine` always did — `monotone_woe_params` containing `n_jobs`/`chi2_p`/`chi2_init_size` used to raise TypeError on the self-fit path (CDC's CMP config carried `n_jobs: 4` and only survived by always taking the reuse path).

**Durable lessons:**
- "WOE table bit-identical" does NOT imply "design matrix bit-identical" — the reused artifact's table is fit-frozen while the matrix is transform-time. Equivalence regressions must diff the transform OUTPUT (or at minimum per-feature coverage stats) alongside the table; the field report burned a day comparing tables while the matrix held a near-constant column.
- Coverage ratios beat occurrence counts for transform-time alarms: the unseen guard scoped to observed-but-unfitted values was structurally blind to an all-NaN column ("0.0% affected"), while missing-rate drift versus fit time catches it immediately. Alarm on the dominant silent bucket, not just the exotic one.
- A str() fallback that bridges dtype drift is a double-edged crutch: it makes int-coded columns "work" against str-fitted tables right up until renderings collide (zero-padding, "1.0" vs "1"), then mis-maps silently — and unseen detection cannot fire because every rendering is known. Bridges need their own tripwire (fallback-hit count > 0 warns).
- Before blaming the pipeline version in an A/B rerun, health-check the input columns against the frozen baseline (dtype, missing rate, unique values). Here the "0.6.8 regression" was a data-prep regression wearing a version-upgrade costume; the only true version bugs were the missing tripwires and a latent TypeError.

## G06-2 — native VIF gate crashed on categorical survivors (CDC field report 2026-07-17, fixed in 0.7.1 — the 0.7.0 tag was burned pre-release)

Found while the CDC project migrated its gap_controls iterative VIF to the native `vif_enabled` gate: `Screen_Gates.apply_vif_stage` fed **raw feature columns** straight into `FeatureSelectionAnalyzer.compute_vif` → statsmodels OLS. Any categorical survivor killed the whole selection — object columns with `ValueError: could not convert string to float`, StringDtype with `TypeError: ufunc 'isfinite' not supported` (inside `statsmodels _handle_constant`). The corr stage had `corr_use_woe_bins`; the VIF stage had no basis switch and no non-numeric handling at all. The report's minimal repro reached VIF only because FVP defaults `corr_use_woe_bins=True` — on the CMP-path unweighted screen the same data dies earlier at the corr stage (the still-open F3-sibling raw-Pearson crash, deliberately scoped to CorrelationFilter primitives).

- **Fix (raw basis, default `vif_use_woe_bins=False`):** non-numeric survivors are excluded from the VIF matrix, kept in the selection untouched, and named in a UserWarning; the VIF summary now persistently records the excluded count/list because application warning filters may hide the warning. If fewer than `max(2, vif_min_features)` numeric columns remain the stage skips with `note=skipped_insufficient_numeric`. Native bool and pandas nullable numeric/boolean columns are cast only in the VIF matrix (to float64); normal NumPy numeric frames remain byte-identical.
- **Fix (WOE basis, `vif_use_woe_bins=True`):** VIF runs on a truly lazy WOE-encoded INS view (`_vif_woe_frame_fn`: adapter construction + transform happen only when the gate runs, then columns are renamed back to raw names), so flag-off opaque prefitted engines preserve legacy behavior. The helper respects a custom WOE suffix, transforms a copy, and turns partial prefitted-engine coverage into an actionable ValueError instead of a bare KeyError. `_needs_woe_bins` counts `vif_enabled AND vif_use_woe_bins`, so the screening binner is fitted even when psi/iv/corr all use raw values; FVP `selection_config_snapshot` records the flag. Categorical WOE-VIF requires `woe_engine="monotone"`: equal-frequency `WOE_Master` cannot fit categorical source columns on this path and now fails before fit with an explicit instruction rather than a TypeError/keep-all swallow.
- The defect report's third ask (per-round VIF trace) already existed: `stage_tables["vif"]` records iteration/dropped/vif/n_remaining and `dropped_detail` gets `stage=vif` rows — pointed out in the reply rather than re-built.

**Durable lessons:**
- When one screen stage gets a `*_use_woe_bins` switch, audit every later stage that consumes feature values — corr got the switch and the categorical warning treatment in F3, VIF got neither and crashed on the exact same inputs one stage later.
- A gate that crashes on a feature it was never going to act on (VIF is only meaningful over numeric collinearity) should exclude-and-warn, not die — same doctrine as F3's "categoricals warned + kept, never dedup-dropped".
- Lazy must include every side effect: constructing an adapter can reject an opaque legacy object even if no transform runs. Create WOE adapters only inside the opt-in gate closure, and test flag-off paths with a deliberately opaque prefitted engine.
- Test-harness trap (Python 3.14): a lazy import or lazy runtime init that happens INSIDE `catch_warnings(record=True)`/`pytest.warns` (statsmodels inside the gate, pyarrow on first StringDtype deep-op) rewrites warning routing and the recorder misses genuinely-emitted warnings. Eager-import in the test module helps for import-time cases; for runtime-init cases assert emission via a `warnings.warn` spy and keep capturability asserted on a stable scenario.

## 0.7.0-R1 — unweighted corr stage crashed on categorical survivors (CDC field report 2026-07-18, fixed in 0.7.1 — first shipping 0.7.x release; 0.7.0 was never published)

Closes the forward pointer in G06-2 ("the still-open F3-sibling raw-Pearson crash, deliberately scoped to CorrelationFilter primitives"). Both `CorrelationFilter` classes — legacy/base in `Feature_Insights.py` and the WOE-aware patch in `WOE_Engine_Feature_Patch.py` — always built the correlation matrix as `self.data[varlist].corr(...)` over raw values, so any categorical survivor (str/StringDtype) reaching the unweighted corr stage killed the whole selection with `ValueError: could not convert string to float`; `corr_use_woe_bins` only ever fed the IV tie-break metric, never the matrix basis. The report reads as a 0.7.0 regression because the 0.7.0 governance defaults let categorical survivors actually travel to corr on the unweighted path (the same 0.6.8 run died one stage later, at the then-unfixed VIF gate) — the corr primitive was broken all along. The weighted path was immune from day one: `Weighted_Screen._weighted_pearson_corr_matrix` already excluded non-numerics as NaN rows plus one UserWarning, exactly the semantics the unweighted side now adopts.

- **Fix (base class raw basis; patch class without a usable binner):** new `_corr_matrix_frame` builds the matrix on the numeric subset; non-numeric columns go to `_corr_matrix_excluded`, are named in at most one UserWarning (W1) per matrix build, and re-enter `_high_corr_pairs` as NaN rows/cols via `matrix.reindex` — the pre-existing `np.isfinite` mask keeps them out of every pair: warned + kept, never dedup-dropped, never crash. A pure-numeric varlist returns `self.data[varlist]` verbatim, byte-identical to the legacy matrix.
- **Fix (patch class, `corr_use_woe_bins=True`):** mixed matrix basis — numeric columns stay raw (byte-compatible numeric dedup), categorical columns are WOE-encoded via the screening binner (`as_woe_engine`, encoded column renamed back to the raw name) and participate in dedup like any other column, so categorical twins genuinely deduplicate (pinned: exactly one of an exact `region`/`region2` twin pair survives). Columns the binner cannot encode fall back to exclude + one distinct UserWarning (W2).
- **Cache validity:** `_high_corr_pairs` reuse condition widened to `set(varlist) <= set(cache.columns) | _corr_matrix_excluded`. Exclusion is a deterministic per-column function (dtype / binner coverage, independent of the rest of the varlist), so the widened predicate can never validate a stale matrix — and without the widening every post-exclusion call would fail the subset test and rebuild+rewarn once per filter iteration.
- **Deliberate asymmetry (review NIT-4):** at `corr_use_woe_bins=True` the weighted basis WOE-encodes *every* column while the unweighted basis keeps numerics raw to honor the byte-compatibility red line, so numeric–numeric dedup can diverge between weighted and unweighted even at w≡1 on this switch. Raw-basis w≡1 parity is exact (pinned); the WOE-basis parity test pins only basis-independent outcomes, by design.
- **NIT-2 hardening (closed same day):** the `as_woe_engine` construction (and the adapter suffix read) now sits *outside* the transform fallback — an unsupported/misconfigured screening engine at `corr_use_woe_bins=True` raises a contextual `TypeError` ("corr_use_woe_bins=True routed categorical feature(s) through the screening WOE engine … Unsupported WOE engine. Expected WOE_Master, MonotoneWOEBinner, or WOEEngineAdapter.", original chained via `from`) instead of soft-excluding every categorical behind a misleading "refit" W2. Transform-level failures on a *supported* engine keep the soft exclude+W2 degrade (deliberate boundary), and the pure-numeric early-return still never touches the engine in the matrix build (pinned: loud raise fires before any W1/W2 is emitted; broken engine + pure-numeric varlist yields a byte-identical silent matrix). Known asymmetry, pre-existing and out of scope: with a non-None binner, `remove_highly_correlated`'s IV-metric path (`_metric_summary` → `get_var_analysis_report`) constructs the adapter unwrapped, so a genuinely bad engine also raises there even on pure-numeric varlists — symmetric hardening is a candidate if it ever field-reports.

**Durable lessons:**
- A fix that excludes columns from a cached matrix must widen the cache-validity predicate too (treat "columns ∪ excluded" as the cache key), and must argue that exclusion is deterministic so the widened predicate stays sound — otherwise you trade a crash for per-iteration rebuilds and a warning storm.
- `pytest.warns(match=...)` proves "at least one", never "exactly one": pin warning counts (`len(family_filter(caught)) == 1`) wherever the contract says "at most one per build" (review NIT-3).
- "Caller frame untouched" must be pinned value-level (`assert_frame_equal` against a deep copy), not by dtype-dict equality (review NIT-1).
- When a defaults flip lets survivors travel one stage further, a latent crash in the next stage presents as a "regression of the flip". The F3 corr-warning → G06-2 VIF → R1 corr-matrix chain is one defect family surfaced one stage per field report — audit *every* downstream value-consuming stage the first time.

## 0.7.2 — regression-boundary hardening (audit 2026-07-18)

The full 0.7.1 regression archive exposed several boundary contracts that happy-path tests did not pin. 0.7.2 closes them without changing the documented opt-in switches:

- **Format-A tables were visibly stable but not lossless.** Default numeric labels intentionally use `.8g`; reconstructing from that text changed high-precision edges, collapsed sparse bin IDs, reset non-default `missing_woe`, and split categorical members whose values themselves contained the display separator. Tuple categories also exercised pandas' list-like comparison edge. `get_final_bins()` now binds exact edges/bin IDs/category members/`missing_woe` to the visible rows through checksummed `DataFrame.attrs["smf_woe_format_a"]`; direct handoff and pickle round-trip exactly. Missing, stale, malformed or hostile attrs fall back to the visible-label contract, so CSV/Excel remain deliberately lossy but usable. Numeric values exactly equal to an edge now honor the displayed right-closed interval `(lo, hi]`.
- **Categorical governance stopped at the numeric fit path.** `small_bin_policy` now applies during categorical fit for `merge`/`warn`/`raise`; merge reuses the categorical clustering core and never crosses `min_n_bins`. Composite/hashable tuple categories survive fit, export, load and apply. A transform value resolved by the supported `str()` dtype fallback is no longer also reported (or raised) as unseen; only values unmatched after both exact and fallback lookup enter `_unseen_category_stats`.
- **FVP kept only the engine's last transform diagnostics.** INS/OOS/OOT calls overwrite the engine-local maps, and batch slimming discarded the heavy engine that held them. FVP now deep-snapshots categorical coverage and unseen stats per target/split/feature, keeps those lightweight maps through slim batch results, deep-merges them across batches, and raises on conflicting duplicate evidence instead of last-write-wins. Slim results also drop the heavy `screening_artifact` reference.
- **Weighted VIF was still unweighted.** The native gate did not pass `weight_col` to `compute_vif`. Non-constant weights now use statsmodels WLS auxiliary regressions; no weights and every constant-weight vector deliberately reuse the legacy OLS call for exact parity. Unsupported `vif_tie_break_metric` values fail at the gate instead of being silently treated as IV.
- **Constant-weight corr and WOE-basis corr diverged from the unweighted contract.** Under the default `pairwise` NaN policy, constant positive weights now reuse the unweighted decision ordering and IV tie-break while preserving the seven-column `corr_dropped` audit, including the actual kept/dropped endpoints. Explicit non-default NaN policies stay on the weighted implementation. `corr_use_woe_bins=True` now matches the mixed basis (numeric raw, categorical WOE), honors custom suffixes, transforms a copy, and warns/keeps categoricals absent from a partial engine rather than shrinking or corrupting the matrix.

**Durable lessons:**
- If a weighted API promises frequency-weight semantics, test both a decision-flipping non-constant vector and exact `w ≡ c` parity; either fixture alone misses half the contract.
- Display tables and serialization artifacts have different precision requirements. Keep human-readable labels stable, bind hidden exact metadata to both its content and row identity, and make the attr-less fallback explicit.
- Mutable engine diagnostics are call-local scratch state. Any pipeline promising split-level audit evidence must snapshot immediately after each transform and preserve the snapshots independently of heavy fitted objects.

## By-group WOE chart IV used full-sample denominators (user report 2026-09-17 on 0.8.0, fixed in 0.8.1)

User report: on `MonotoneWOEBinner.plot_woe_graph(group_name=...)` charts the per-group IVs sat far below the overall chart IV, suspected to be computed on the full sample. Requalified against 0.8.0 with a render-capture repro: the hypothesis is **correct**, and review surfaced compounding defects.

- **Root cause 1 — denominators.** All three bar modes (`pooled`, default `clustered`, `small_multiples`) divided each group's bin counts by the normal-row bad/good totals of the whole `_df_for_group`. With group shares s_B/s_G of total bads/goods the shown IV is Σ(s_B·b_i − s_G·g_i)·[ln(b_i/g_i) + ln(s_B/s_G)], ≈ s × in-group IV when s_B ≈ s_G. Four homogeneous equal groups showed 0.17–0.19 against in-group IVs of 0.69–0.76 (overall 0.723); with unequal bad rates the shrink factor varied per group and the shown IVs summed past the overall IV, so the numbers could not even be rescaled.
- **Root cause 2 — special bins omitted.** Only normal bins were summed while the overall chart shows `vr["iv"]` = normal + special/missing bins (a 20% informative missing bin: overall 0.993 = 0.718 + 0.275).
- **Found in review — eps inflation.** With per-group denominators a bin holding 0 bads (or 0 goods) inside a group adds ≈ pct·ln(pct/eps) ≈ 0.6 of phantom IV: 12 months × 5,000 rows at a 3.6% bad rate showed 0.93–0.97 in the three months with one zero-bad bin (population in-group IV 0.349).
- **Found in review — loaded binners.** `get_final_bins` → `load_woe_bins` dropped `sv_policy_applied` and the fitted smoothing parameters, so governed fits could not be mirrored after a Format-A round trip.
- **Found in review, pre-existing — sparse bin ids.** By-group bars and lines iterated `range(n_normal)`; with fitted bin ids [0, 2, 3] the line rendered as [0.203, nan, -0.134] under the wrong labels and the last bin (WOE −11.87) was never drawn.
- **Fix:** `_group_iv_for_plot` applies the fit-time convention to the group's rows — normal bins over the group's binned normal rows; special cells over all group rows following each fitted row's `sv_policy_applied` (keep → empirical, smoothed with the fitted parameters; neutral / neutral(fallback) → 0; merged_into_missing → folded into the group's `[Missing]`; merge_target → merged, unsmoothed), never re-deciding inside the group. Unsmoothed cells holding a single class inside the group are left out (the `iv_guard` convention of screening IV); laplace-smoothed special cells already have a finite WOE and always count (owner decision on review NIT-1 — excluding them had shown 0.795 against an overall 0.875 on a whole-sample chart); categorical values unseen at fit stay out of the normal base; <5-row and single-class groups still show 0. Governed fits now export `attrs["smf_woe_format_a"]["sv_decisions"]` (per-row policies + smoothing parameters) under a separate `sv_decisions_digest` bound to the base `metadata_digest`; the base digest's key tuple is unchanged, so older loaders keep validating edges/bins/categories, and default-governance attrs stay byte-identical. `load_woe_bins` restores the decisions only when both digests, the row identity and every value validate; a smoothing alpha that cannot round-trip (NaN, huge int) omits the decisions instead of breaking `get_final_bins`. By-group series select rows by fitted bin id and write by position, and when two special values render the same label both the bars and the IV use the first non-empty rows. WOE lines keep the full-sample base; bars, N/TR labels, files, sizes and dpi are unchanged, and no screening or modeling output reads these IVs.
- **Pinned:** whole fit sample as one group reproduces `vr["iv"]` across 12 fit configurations (every unsmoothed fitted cell two-class; a smoothed all-good special cell keeps parity too); binners loaded with default SV parameters reproduce fitted group IVs; a per-group re-deciding mutant fails the multi-group governance tests (the -998 share straddles `sv_min_bin_size` between the whole sample and single groups); rendered WOE lines match the full-sample formula to 1e-12; all 18 review mutants (sparse loops per mode, exclusion rule, merge/smoothing handling, restore gates, digest binding, export source of smoothing parameters) fail the suite.
- **Limits:** CSV/Excel reloads (attrs lost) and Format B carry no decisions, so their special cells count as keep. `-inf` feature values break whole-sample parity: the fit counts them in the normal totals although no bin receives them (pre-existing fit quirk).

**Durable lessons:**
- A per-group statistic needs per-group denominators. A global base is right for comparable WOE *levels* and wrong for any magnitude (IV, KS, lift) — audit each number on a by-group chart separately.
- Pin "whole sample as one group == overall" wherever a chart shows both: one assertion catches wrong denominators and silently omitted components. It cannot tell "follow the fitted decision" from "re-decide per group" — that needs multi-group fixtures whose shares straddle the threshold, verified against an explicit mutant.
- Making a statistic exact on small subsets amplifies eps artifacts (cell shares grow k-fold); reuse the codebase's degenerate-cell convention (`iv_guard`) rather than raw eps.
- Extend a checksummed artifact with a separately digested key bound to the base digest instead of widening the base digest, so older readers keep validating what they understand.

## ParallelApplyEngine process backend broke on joblib 1.6 (CI drift 2026-09-17, fixed in 0.8.1)

Found when the by-group IV fix hit CI: every matrix job failed exactly one test, `test_parallel_engine_row_split_process_preserves_order` (1128 passed / 1 failed in all six), unrelated to the diff. joblib 1.6.0 (released 2026-08-31, after the 0.8.0 CI run) removed the vendored `joblib.externals.cloudpickle` and now `Requires-Dist: cloudpickle>=3.0`. `ParallelApplyEngine._validate_picklable` imported the vendored module *inside* the try block that converts any exception into "func, func_args, and func_kwargs must be serializable for backend='process'", so with joblib ≥ 1.6 every process-backend run failed with a TypeError blaming a perfectly serializable callable. Local runs stayed green because the WSL venv pins joblib 1.5.3.

- **Fix:** resolve the serializer before the check — vendored copy when present, otherwise the `cloudpickle` package (a joblib ≥ 1.6 dependency, so no new SMF requirement); an import failure now surfaces as ImportError.
- **Pinned:** a test hides the vendored module and asserts serializable callables validate, non-serializable arguments still raise TypeError, and a missing serializer is an ImportError. Verified against a real joblib 1.6.0 install: the old engine fails 2 tests in `test_parallel_engine.py`, the fixed one passes 8/8.

**Durable lessons:**
- Never import inside the `try` whose `except Exception` rewrites errors into a domain message — an environment problem then masquerades as a user error. Resolve dependencies first, then guard only the operation being validated.
- `joblib.externals.*` (and any vendored `externals` namespace) is private and can vanish in a minor release; prefer the public package, falling back to the vendored copy only for old versions.
- An unpinned CI matrix will surface dependency drift on whatever commit lands next. When CI fails on a file the diff never touched, compare installed versions against the last green run before suspecting the change.

## `load_woe_bins` rejected dict-wrapped Format A tables (found in review 2026-09-17, fixed in 0.8.1)

`load_woe_bins({feat: {"bin_df": table}})` — the documented "Format A wrapped in a dict" branch — picked the table with `payload.get("bin_df") or payload.get("df")`, which asks the DataFrame for its truth value and raised "The truth value of a DataFrame is ambiguous" every time. `{"df": table}` only worked because `None or table` never evaluates the frame. Fix: explicit `None` checks (`bin_df` preferred), plus a ValueError naming the type when the wrapped value is not a DataFrame. Pinned: both keys load identically to the bare table (exact edges via attrs, same `apply_woe` output).

**Durable lesson:** never use `a or b` / `if frame:` to choose between pandas objects — test `is None` explicitly; the `or` form can silently "work" for whichever operand happens never to be truth-tested.

## Declared special values absent from the fit sample were scored as ordinary numbers (user report 2026-09-17 on 0.8.1, opt-in fix in 0.8.2)

User report: a declared sentinel (`special_values=[-1]`) that never occurs in the fit sample gets no special bin; the by-group chart and group IV drop those people, while scoring puts `-1` into the "0 cards" bin. Requalified on 0.8.1: correct, and one behaviour wider.

- **Three behaviours for one value.** `apply_woe` builds its special-value map from the fitted `sv_table` only, so `-1` fell into the lowest normal bin (817 rows all took the `(-∞, 0]` WOE 0.4845, no warning); the screening/PSI adapter is built on `apply_woe` and agreed. The by-group chart and `_group_iv_for_plot` split rows by the *declared* list and dropped them (bars summed to 89.8%; group IV 0.2252 against 0.2776 under the scoring convention). A Format-B load fabricates `[sv=-1]` from the declared list and scores `missing_woe`. Present since at least 0.8.0; reported and fixed for MonotoneWOEBinner only (`WOE_Master` handles its own `fit(spec_values=...)` and was not re-examined).
- **Fix (0.8.2, opt-in):** `unseen_special_policy`. `"normal_bin"` (default) keeps legacy scoring and makes the chart split only special values that have a fitted row, so charts and group IV bin those rows exactly like scoring. `"neutral"` appends one placeholder row per absent declared numeric value after all SV governance (n=0, WOE=`missing_woe`, IV=0, `sv_policy_applied="unseen_at_fit"`), so scoring, screening and charts treat the rows as special and the group IV leaves them out; the rule lives in a visible table row and survives Format-A and attr-less reloads. Fit records `_unseen_special_at_fit` (one aggregated UserWarning under `normal_bin`); `apply_woe` records `_unseen_special_stats` and warns per feature unless `unseen_category_policy="silent"`. NaN and categorical features are out of scope. FVP/CMP monotone defaults and both `_MONOTONE_INIT_KEYS` carry the key; FVP freezes the transform stats per split (`unseen_special_stats_by_split` / `woe_artifacts["unseen_special_stats_by_target"]`). CMP's monotone self-fit used to inject `special_values=[-999999]` unconditionally — absent from almost every feature, so every run would warn and, under `neutral`, every table would carry a placeholder; since 0.8.2 it declares the sentinel only when the WOE fit sample contains it (owner decision; binning and scoring are identical either way, explicit `special_values` untouched). Default planned to flip to `"neutral"` in 0.9.0.
- **Found in adversarial review (fixed in the same release):**
  - *Fractional labels aliased ordinary values.* `apply_woe` parsed every `[sv=x]` label into `float(x)` **and** `int(float(x))`, so a `[sv=0.5]` bin also captured value `0` (on 0.8.1, 4,174 of 16,000 ordinary `0` rows took the `[sv=0.5]` WOE -0.0629 instead of their bin's 0.4882). Present since the first release for fractional special values present at fit; `neutral` placeholders would have made it reachable from absent ones. The int key is gone (for integer values it was always the same dict key as the float); non-finite labels keep their text key as before.
  - *Text vs number.* Chart splitting, fit records and transform detection first matched `_sv_label(declared)` text while scoring matched parsed numbers, so a loader declaring `-1.0` for a table fitted with `-1` reported false "unseen" rows and charted them as ordinary. All three now parse the fitted table with the same helper as `apply_woe` (`_sv_table_entries`, numeric comparison); placeholders are created only for numeric declarations and deduplicated by value (`"-1"` or `["-1", -1]` no longer yield a placeholder that hijacks a real `-1`).
  - *Invisible warnings.* The import-time `warnings.filterwarnings("ignore")` silenced every new warning in ordinary sessions, so they are also sent to `logger.warning`; the global filter itself was removed in the same release (next entry).
  - *Round 4 (after the first fixes):* an `isin` prefilter added to skip the per-value scan made default-path `apply_woe` 2.3-2.6x slower (pandas `Series.isin` costs ~50 ms per 1M-row column; plain per-value `eq` costs ~0.9 ms), so it was removed; the chart split let one row match two table rows that parse to the same number (Format B with `[-1, -1.0]`, or ints above 2**53) and double-counted them — now the first matching row claims it; sub-threshold `neutral` governance rows were one mutant away from being reported as "unseen" with no test noticing.
- **Known limits:** `_unseen_special_stats` describes only the latest `apply_woe` call (the WOE adapter's `assign_bins_many` calls it in 64-feature blocks); `-inf` declared special values are binned by `searchsorted` in scoring but dropped by `pd.cut` in charts; under `neutral`, `iv_summary` counts placeholder rows among special bins and adapter PSI labels pool rows whose WOE strings coincide (e.g. placeholders and NaN rows both at `missing_woe`); a 0.8.1 loader rejects the whole `sv_decisions` payload of a table containing `unseen_at_fit` (unknown policy), so its group IV falls back to no decisions (scoring unaffected); text such as `"-1"` in an object column is scored like `-1` but not counted in the stats. Before the 0.9.0 flip: the default is pinned in the binner and both pipeline default dicts, and config snapshots of user-supplied dicts omit the key.

**Durable lessons:**
- A "declared vs fitted" split is a consistency trap: transform, adapters, charts and loaders must all read the same source of truth. Materialize the decision in the fitted artifact (a visible row) instead of re-deriving it from constructor state at each call site — the constructor of a loading binner may differ.
- A declared sentinel with no fit evidence should never silently inherit a real bin's risk; make the scoring rule visible (placeholder row) and loud (fit and transform warnings).
- Parse serialized labels with one shared function in every consumer, and never derive extra lookup keys (like an int truncation) that can alias ordinary values.
- Check warning visibility in a plain interpreter, not only under pytest: an import-time `warnings.filterwarnings("ignore")` silently disables every loud guard in the package while every test still sees the warning.
- A "cheap prefilter" is not cheap by default — time it on production-sized columns against the loop it is meant to skip before adding it to a per-feature transform path.

## Importing SMF silenced every warning in the process (≤ 0.8.1, removed in 0.8.2)

Found while making the unseen-special-value warnings visible. `Modeling_Tool/WOE/WOE_Monotone_Binner.py` (imported by `import Modeling_Tool`) and `Modeling_Tool/Model/Backward_Tool.py` both ran `warnings.filterwarnings("ignore")` at module level since the first upload. Pinned by `test_import_keeps_warnings_visible.py`, which checks in a fresh interpreter that importing the package (including `Backward_Tool`, which `import Modeling_Tool` loads lazily) adds no broad ignore filter, that probe warnings from user code and SMF modules stay visible, and that the MonotoneWOEBinner fit warning reaches a plain session.
- **What became visible:** a typical FVP + CMP run shows 69 warnings. 50 are seaborn deprecations from `Eval/evaluate_model.py:618-622` (`distplot` with `bw=` kde kwargs — errors in seaborn 0.14), 14 are `divide by zero encountered in log` from `Core/utils.py` `_calc_woe_iv_values` (bins with zero bads or goods), 2 are pandas `concat` FutureWarnings from `Eval/Model_Eval_Tool.py:513`, and 3 are SMF guards. The follow-up batch in the same release removed the noise (next entry); the docs FAQ lists what still shows up and how to filter it.
- **Same class, fixed in 0.8.2:** `import Modeling_Tool` also set `pd.set_option('future.no_silent_downcasting', True)` process-wide (`Core/Binning_Tool.py`, `Core/kDataFrame.py`, `Core/Slope_Tool.py`, `Core/ODPS_Tool.py`), changing downcasting in the user's own pandas code. Impact was measured before removing: with the four calls neutralised the full suite passes (1208) and emits no downcasting warning anywhere, so nothing in SMF depends on the flag. All four removed; the fresh-interpreter probe snapshots every registered pandas option around the import and now allows no deviation at all (the `mode.chained_assignment` carve-out it briefly had was closed by the next batch).
- **Same class, fixed in 0.8.2 (owner chose to fix the call sites):** those same four sites plus `ExcelMaster/Template.py:9` ran `pd.options.mode.chained_assignment = None` at import, and `Report/Report_Tool.plot_woe` set it again when called — disabling pandas' `SettingWithCopyWarning` process-wide, for the user's own code too. It was switched off because SMF tripped it at **nine sites in six modules**; all nine are fixed and the option is gone from all six places.
  - **Finding the sites is the hard part.** Removing the option and grepping the suite log for `SettingWithCopyWarning` gives you the *reporting* line, not the frame that was flagged. The reporting line moves as you fix things, so line numbers in old notes mislead: the original `Sample_Split.py:46` was `oot_df[...]`, not `mdl_df[...]` two lines above. Two things that worked: a `conftest.py` that monkey-patches `warnings.warn` to dump `traceback.format_stack()` for that category (gives the real call chain), and re-running the whole suite after each fix rather than trusting the first grep — `WOE/WOE_Tool.py:546` only showed up after the four `Core` options came out.
  - **One root cause covered three sites:** `Binning_Tool._materialize_bin_columns` is the single choke point all four binning callers share, and `run_binning` → `super_binning` → `WOE_Tool.transform_single` all inherited its flagged frame. Fixed there with `data.copy(deep = False)` — it only *adds* columns, so a shallow copy is enough and binning does not pay for a deep copy per variable (`run_binning` receives the caller's whole training frame and is called once per feature; a deep copy there would be a real production cost). The degenerate empty-data branch in `run_binning` already did `data.copy()`, which is what the contract should have been all along.
  - Other sites: `Core/utils.py` `scoring` (`all_missing_data`), `Sample/Sample_Split.py` (`oot_df`), `Eval/Model_Eval_Tool.py` ×2 (`_mdl_scr`), `WOE/WOE_Plot_Tool.py` ×2. **Behaviour changes (owner approved):** binning no longer writes `bin_num`/`bin_range` back onto the caller's DataFrame, `get_gains_table` no longer leaves `_mdl_scr` behind, and `plot_woe` / `plot_woe_group` (public API) no longer lowercase the caller's column names or replace inf in `woe`/`iv` in place. `scoring` / `select_sample_seed` were noise only — those writes already landed on a copy.
  - **An extra `.copy()` was removed again as an equivalent mutant**: `mdl_df`/`val_df` out of `SampleSplitter.split_df` are not flagged, so copying them killed nothing. Same discipline as `NumVarBinning` in the bool fix — if the mutant survives and you can show the code path cannot differ, drop the code rather than the check.
  - Pinned by `test_no_caller_frame_mutation.py` (13 tests): per-entry-point frame equality, plus six entry points run under `pd.option_context("mode.chained_assignment", "warn")` asserting no `SettingWithCopyWarning` — that parametrized test is what gives the noise-only sites mutation coverage, since their frame-equality checks pass either way.

**Durable lessons:**
- A library must never change process-wide warning (or logging) configuration at import. Suppress a specific warning at its call site with `warnings.catch_warnings()` + a message/category filter.
- A blanket filter hides the library's own technical debt too: the seaborn calls slated to become errors were invisible to maintainers for the same reason.

## Warning noise from SMF's own calls, and the bugs hiding behind it (fixed in 0.8.2)

Once the import-time filter was gone, the full-suite warnings summary (107 distinct warnings) was triaged: SMF guard warnings and informative third-party notices stay; deprecations and floating-point notices raised by SMF calls were removed without changing results; several of them were symptoms of real bugs. The suite's warning count fell from 2394 to about 280.

- **Removed, results unchanged:**
  - seaborn `distplot` / `kde_kws={'bw': ...}` in `Eval/evaluate_model.py` → `ax.hist` + `sns.kdeplot(bw_method=...)`. Two details were needed for pixel-identical charts: distplot drew and removed a `(mean, 0)` point to pick a colour, which still extended the autoscaled y-limits (visible on KDE-only multi-model pages with near-constant or all-NaN scores), and its kde calls drew on pyplot's *current* axes rather than the one passed in (harmless in SMF's callers, wrong for direct callers). The helpers repeat the anchor point and draw on the given axes;
  - `log(0)` in `Core/utils.py` `_calc_woe_iv_values` (±inf WOE kept), lift 0/0 in `calc_fixed_pct`, float-max values overflowing when rounded (`get_bin_range`, `quick_binning` column rounding and pandas formatting `pd.cut` labels) and VIF of perfectly collinear features (inf) → `np.errstate` around those operations;
  - pandas: `get_gains_table(add_func=...)` selects the unique columns (grouping columns included) before `apply`; `cre_pvt` and the percentile aggregation pass `observed=False`; `WOE_Plot_Tool` / `plot_woe_tool` aggregate with `"sum"` / `"max"`;
  - RI default hard cutoff no longer takes the median of all-NaN scores; sklearn "X does not have valid feature names" in the LR statistics helpers (`_predict_positive_proba` restores the fitted column names by position); pyodps `Schema` → `TableSchema` (old name as fallback);
  - shap `summary_plot` global-RNG FutureWarning → `ModelExplainer.summary_plot(random_state=0)` passes `rng` when shap supports it (beeswarm jitter is seeded, so images differ from earlier runs; SHAP values do not).
- **Bug, single-class datasets crashed evaluation:** with only goods (e.g. an OOT window without bads) or only bads, TPR or FPR is NaN everywhere; `summarize_roc` took `np.argmax` of the all-NaN gap, got -1 and looked `thresholds[-1]` up by label → `KeyError(-1)` from `PerformanceEvaluator.evaluate` (plain, weighted, benchmark, grouped, multi-target), `evaluate_performance`, `get_perf_summary`, `comparison_performance`, `plot_roc_curve` and `plot_ks_curve`. The reject-inference pipeline caught it and dropped the evaluator output for every method (`perf_eval_error=KeyError(-1)` on every row). Now KS / AUC are NaN while N, bad rate (0 or 1), average score, top / bottom target rates and the charts are reported for that dataset (owner decision; a branch that would have blanked the whole row, never reached before, now only applies to fewer than two usable rows).
- **Bug, FVP without OOT degraded integer features and the target:** the missing OOT split is a placeholder `pd.DataFrame(columns=work.columns)` (object columns). Concatenating it into `combined` turned int64 features and the target into object. Integer features were reported as categorical, had no IV/KS min / mean / max and were left out of the raw-value correlation matrix; with an object target the correlation filter failed for every feature (`correlated_detail` stayed empty) and PSI without target / WOE bins recorded a TypeError per feature (3 error rows instead of 54 PSI rows on the review data). `Modeling_Tool/_utils/frames.py` `concat_non_empty` leaves empty frames out of row concatenation (column union kept, None skipped, first frame's dtypes kept when all are empty; only `ignore_index` is accepted). Feature selection of no-OOT runs can change (owner: keep and disclose); runs on ≤ 0.8.1 should redo correlation screening. Also used for the gains summaries, whose `N_BUMP` / `N_BINS` no longer turn object when a split is missing.
- **Bug, bool features vanished from FVP distribution summaries** on every path (`describe()` drops bool columns mixed with numeric ones); they are now reported in the categorical table.
- **Bug, bool features broke every quantile-based binner (fixed 0.8.2):** numpy refuses percentiles of a bool array (`TypeError: numpy boolean subtract, the '-' operator, is not supported`), so `quick_binning`, `super_binning`, the gains table, `WOE_Master`, `MonotoneWOEBinner.fit`, `feature_screen` and `weighted_feature_screen` all raised on a bool column that worked the moment it was cast to int8. In FVP with the WOE stages on it surfaced as a swallowed "feature insights failed" warning plus `KeyError: WOE column 'x_woe' was not produced`, killing the run. `Modeling_Tool/_utils/frames.py` `as_binning_numeric` maps bool to int8 (nullable `boolean` to `Int8`, so missing values survive) and returns every other dtype unchanged; it is applied at exactly the two load-bearing sites, `Binning_Tool.quick_binning` and `WOE_Monotone_Binner._greedy_fit_one`. Results are bit-identical to the int8 copy of the same column; only the WOE table's `MIN`/`MAX` still report the feature's own `False`/`True`. **`NumVarBinning.calc_equi_cutpoints` / `modify_cutpoints` were deliberately left alone**: a bool column has at most two distinct values, so the `len(unique) <= bins` short-circuit always returns before the percentile call, and converting there is an equivalent mutant (verified — identical output at `bins` 1, 2 and 4). Pinned by `test_bool_feature_binning.py`.
- **Bug, one-column Excel tables lost their title:** `ExcelMaster.merge_col` merged a 1×1 range; xlsxwriter refuses (`Can't merge single cell`) and writes nothing. Single cells are now written directly with the title format.
- **Kept on purpose:** SMF guard warnings; seaborn's zero-variance notice (a KDE curve is skipped); sklearn `UndefinedMetricWarning` on single-class data; sklearn calibration's note that `sample_weight` only reaches the calibrator (weighted semantics); xgboost "Parameters not used" (sklearn-style keys passed to `xgb.train`); matplotlib `tight_layout` notices from tiny test canvases; third-party internal deprecations.

**Durable lessons:**
- Triage a warning before silencing it: an `argmax` FutureWarning, a `concat` FutureWarning and an xlsxwriter notice each marked a genuine defect.
- Empty placeholder frames (`pd.DataFrame(columns=...)`) are not neutral in `pd.concat`: their object dtype leaks into the result and can silently disable downstream stages. Build placeholders from the real frame (`df.iloc[:0]`) or leave them out of the concat — and measure every consumer when the dtype changes back.
- When a guard (try/except + warning) catches an exception on a routine path, the warning text is a bug report — follow the original error.
- Replacing a deprecated plotting call needs a pixel comparison, including degenerate inputs: hidden side effects (a removed anchor artist, the current-axes default) change autoscaling and targets.

## End-to-end audit of `CreditModelPipeline` and `FeatureValidationPipeline` (audit 2026-10-08; fixed after 0.8.2, unreleased)

Both pipelines were run on synthetic data with known properties (strong feature, near-duplicate, constant, drifting, high-missing, special values, weights, OOT) and every stage was compared with an independent recomputation. About 60 defects were fixed with regression tests (216 in `SuperModelingFactory_pytest/test_pipeline_e2e_audit.py`; every defect has at least one test that fails on the unfixed package). The full list is in the doc repo's `changelog/unreleased.md` (section 5) and `SuperModelingFactory_pytest/ENVIRONMENT.md` (section 4). Families, with the one example that explains each:

- **Silent swallow of a failure.** A constant feature crashed the screening plots (`get_decision_tree_binning_edges` returned a tuple); `CreditModelPipeline` caught every screening exception, kept every feature and said nothing. The screening failure now warns, and `on_empty_stage='raise'` propagates as `EmptyStageError`.
- **Two code paths that must agree did not.** `fit` filled missing values with -999999 while `transform` used `missing_ref_value`; FVP, the screening engine and CMP declared the `-999999` special value differently (`with_default_special_values` is the single rule now); `woe_table` was recomputed from raw counts instead of reporting the applied mapping; the DataFrame and the CSV batch paths inferred `new_feature_cols` by different rules and the batch path did not read grouping columns; batch mode promoted unlabelled rows to INS.
- **Index labels instead of positions.** `SampleSplitter.split_df` used `df.loc` on index labels, so a duplicated index (after `pd.concat`) duplicated rows and leaked INS into OOS.
- **Hand-off without a contract.** An artifact could carry a split, a WOE engine or a feature list that the credit-model run then ignored or contradicted. The artifact now records its split settings; mismatches, features without bins, a missing engine and replaced `target_col`/`weight_col` warn or raise.
- **Parameters that reached only half of the pipeline:** `corr_params['method']`, `woe_suffix`, `random_state` (backward proxy, CatBoost `random_seed`), `on_empty_stage`, `eval_weight_col=None`.
- **Resource blow-up:** `ExcelMaster.set_cell_size` wrote the height of all 1,048,576 rows per sheet; the default 20-sheet report needed about 10 GB.

Opt-in switch, default unchanged: `MonotoneWOEBinner(sv_total_basis='all')` measures every bin against the totals of all rows (the textbook scorecard base); the default `'ordinary'` measures ordinary bins against the ordinary rows and special/`[Missing]` bins against all rows, which overstates IV (1.20 vs 0.89 in the test) and can rank a riskier special bin below a safer ordinary one — recommend `'all'` for LR. Opt-in switch, default unchanged: `warm_start_score_scope='full'` adds the warm-start prior to the early-stopping validation set (`eval_init_score`), to the Optuna scoring (`param_search(eval_init_scores=...)`) and, as the group `warm_start_prior`, to the Owen explanation; the default `'train'` leaves them on the increment alone (Optuna table AUC 0.726 vs 0.743 for the evaluated model in the test). SHAP importance of the trees does not depend on the prior. Batch-mode selection fixed: per-feature stages in each batch, then the full selection once on the candidates (it was the union of per-batch selections: correlated twins of different batches both kept, 3 features under a cap of 1, a batch whose features all failed IV kept them, no WOE engine in the artifact). Weighted screening on WOE bins now counts class-pure bins with the engine's 1e-6 floor like the unweighted one (`iv_guard` had dropped them: IV 0.09 with unit weights vs 3.08 unweighted). Cosmetic outputs fixed (names changed, update code that reads them): quantile columns are `Q<percent>` (`Q50`, `Q2.5`), the PSI sample dimension is `sample` (was `_smf_split`), chart folders appear only when a chart is written, WOE charts are drawn once, recorded paths are absolute. Documented, not changed: `perf_min_bin_prop` is a target; a reused `output_dir` keeps files of earlier runs; without WOE bins the weighted (equal-frequency) and unweighted (gains-table) screenings bin differently, so their IVs differ even with unit weights.

**Durable lessons:**
- A test double of "the other path" is the cheapest audit: for every output that two paths produce (batch vs not, artifact hand-off vs self-fit, reported table vs applied mapping, raw vs WOE frame), compare them on data with a sentinel, a missing label, a duplicated index and a weight column.
- Read a tuning parameter's effect, not its presence: five parameters were accepted and reached only the report, not the stage they were named after.
- A documented limitation that is also a bug looks the same in the docs (`min_n_bins` "can end one bin below" was the off-by-one itself); when a doc sentence describes an exception to the parameter's own meaning, check it against the code.
- Probe on frozen copies: run the full suite on a copy of the package while editing the working tree, and prove each new test fails on a snapshot of the unfixed code.
- Sharding a pipeline (feature batches) is only exact for stages that judge one item at a time. Stages that compare items (correlation, VIF) or count them (caps) must run once on the merged survivors; a union of per-shard results is a different algorithm, and a per-shard fallback (keep all when a stage empties the shard) leaks items the global run drops.
